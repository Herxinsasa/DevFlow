# Code Review - 代码审查调度

## 定位

`code-review` 是产品代码交付前的独立审查控制面。它负责确定范围、整理最小充分上下文、通过 `subagent` 调度 `code-reviewer`、处理返回结果和写入审查凭据；不亲自执行代码审查，也不直接修改代码。只有满足待用户验证说明预览条件时，才路由 `code-committer` 生成只读预览。

DevFlow 的 Skill、Agent、Hook、模板和工作流说明属于工作流维护，不进入本 Skill，也不生成产品代码审查凭据。

## 触发场景

- 需求开发的关联编码任务完成，需要统一审查本次代码差异；联调 Bug 批次等到下一版本准备交付。
- 用户要求“审查代码”“代码评审”“评审本次变更”“code review”或“看下这次改动风险”。
- 下一版本准备交付或准备提交产品代码，但审查凭据缺失、失效或未覆盖当前代码。

用户自测、联调或系统测试期间的连续 Bug 修复不逐项触发；用户明确要求、下一版本准备交付或准备提交时，对本批次累计最终差异统一做一次独立审查。审查后有修正时仅增量复审受影响部分，最终凭据须覆盖完整交付范围。没有产品代码变更时不触发。

## 工作原则

1. **独立审查。** 首次通过 `subagent` 使用新的 `code-reviewer`，不让编码者自审冒充独立结论。
2. **事实优先。** 以实际 diff、已确认需求与设计、源码和适用项目约束为依据，不把历史讨论或 reviewer 标签直接当作事实。
3. **范围明确。** 默认审查本次交付的全部代码差异；允许部分审查，但必须标明未覆盖范围，且不能作为最终提交凭据。
4. **最小上下文。** 只传入判断本次改动所需的事实，不倾倒无关文档和执行流水。
5. **问题优先。** Critical、Important 必须处理；Suggestion 只记录。涉及行为、范围、契约或验收选择时列为待确认，不代替用户决策。

所有产品代码交付都需要独立审查。`code-reviewer` 角色 Skill 不可用或当前 Harness 无法启动子 Agent 时不得写通过状态：T0/T1 可继续本地验证但不能提交，T2/T3 停止交付并通知用户。

## 输入

- 审查范围、实际变更集、变更文件和迭代开始时的工作区基线。Git/SVN 使用其 diff；无版本控制时使用基线快照与当前文件比较。
- 关联需求规格、技术改造目标或修复批次中的既有预期、失败证据和验收标准；有开发计划时读取计划，交付后修复批次不补造计划。必要时引用原已确认契约。
- 判断实现契约所需的设计；涉及 UI 时按需提供已确认的 UI 业务事实、原型或界面稿。
- 已执行的局部验证、失败证据、已知限制和未覆盖项。
- 本次变更适用的项目约束、同层同类参考符号及真实调用路径、权威类型、适用扩展机制和文件格式检查结果；从各任务恢复信息提取关键定位并对实际源码复核。

解析代码约束时按总控的用户注入文档冲突确认与优先级规则执行；读取项目根 `AGENTS.md` 或 `CLAUDE.md`、项目规范、既有一致代码风格，以及解析后的 `coding`、`logging` 领域约束（无配置时使用 `.devflow/constraints/` 默认基线）。只传入与本次变更相关的约束，不在 Skill 内硬编码语言、框架、注释或日志规则。

## 工作流程

### Step 0：检查 reviewer

确认 `code-reviewer` 角色 Skill 存在，且当前 Harness 能启动独立子 Agent。DSH 使用 `subagent`（不使用 `subagent_fork`），并在 prompt 第一句要求子 Agent 先调用 `skill` 加载 `code-reviewer`；主 Agent 不得直接加载 `code-reviewer` 自审。Agent 或角色 Skill 不可用时不得由主 Agent 模拟审查，也不得写入审查通过凭据。

### Step 1：确定审查范围

根据迭代或修复批次的交付基线、初始已有改动、任务或 Bug 目标文件和实际变更集确定本次范围，不把无法证明属于本次交付的用户原有改动纳入结论。

Git 仓库包含多个 DevFlow 项目时，默认范围限定为本次待交付文件所属的当前 DevFlow 项目，不等同于整个 Git 仓库。根据文件向上查找最近的 `.devflow/progress.json` 确定归属；读取 Git 差异时使用项目路径限定，并排除归属于更深层 DevFlow 项目的文件，不能仅凭 Git 根或命令执行目录推断范围。待交付文件跨多个 DevFlow 项目时按项目拆分审查并分别写入凭据。

完整审查表示覆盖本次待交付的全部文件，不表示覆盖整个 Git 仓库或项目内所有未提交修改。完整评审多个文件后只提交其中一部分，只要暂存文件均被凭据覆盖，仍是有效的完整审查；只有待交付文件未全部审查时才属于部分审查，并必须记录未覆盖范围。

### Step 2：整理审查上下文

组装范围、变更集、需求与验收、必要设计、验证结果、适用约束、每个任务或 Bug 的实现依据和已知限制。交付后批次传入测试版本基线、稳定 `BUG-xxx` 的诊断与局部复测、累计最终差异，不要求新建需求规格或开发计划。关键参考符号、权威头文件或契约、机制适用结论和文件格式检查结果必须能对应实际修改文件；缺失则先取证，不把“已遵守项目风格”的摘要当证据。路径足以让 reviewer 读取时优先传路径与相关章节，不重复粘贴整份文档。

没有 UI 影响时不读取 UI 产物；T0/T1 不为审查补造 T2/T3 文档。

### Step 3：派发独立审查

DSH 中首次派发时通过 `subagent` 启动新的独立子 Agent，prompt 第一句要求其先调用 `skill` 加载 `code-reviewer`；主 Agent 不得直接加载该角色 Skill。prompt 必须包含 Step 1/2 的范围、变更集、基线、需求与设计路径、验证结果、适用约束和已知限制，并说明子 Agent 看不到当前会话。要求子 Agent 先列候选问题，按 Critical、Important、Suggestion 排序，并为每项给出文件位置、事实证据、实际影响、置信度和建议测试重点。reviewer 只输出结论，不修改文件。等待子 Agent 完成通知并核对返回结果后，才进入 Step 4；未收到结果前不得写审查通过凭据。

### Step 4：复核并路由结果

reviewer 输出是候选结论。根据当前事实源复核问题是否成立，再按结果路由：

- 确认的实现缺陷返回编码或修复阶段。
- 需求、影响面、UI 行为或技术契约缺失时返回对应前置阶段。
- 存在多个合理方案，或处理会改变行为、范围、契约、验收时，集中列为待确认并暂停相关修改。
- Suggestion 只记录；缺少证据或与当前事实不符的问题说明反证后驳回。

不得因为 reviewer 标记了 Important 就自动扩大修改范围。待确认项未确认前不得进入修复。

### Step 5：复审

问题修复后只增量复审相关变化。DSH 中优先用 `send_message` 续用同一 `code-reviewer` 子 Agent，保留其已读上下文；仅在子 Agent 已结束且无法续用、或上下文已失效时新建，并记录原因。最终通过凭据必须覆盖准备交付或提交的全部产品代码差异；任何审查后的代码变化都会使对应凭据失效。

### Step 6：记录结论

结论使用：通过、有条件通过、不通过、输入不足、待确认。

- T0/T1 无阻塞问题时，只写审查状态和一句结论。
- T2/T3 或用户要求归档时，使用总控解析的 `code_review` 模板（默认 `references/代码审查报告_模板.md`）写入 `docs/07-审查/<迭代ID>-代码审查.md`，只保留结论、问题、覆盖范围、风险和处理路径；本模板不可读取或语义有疑问时提示用户处理，审查结论按实际证据报告，不虚报归档或审查通过。
- 通过或有条件通过时写入 `.devflow/.review-status.json`，记录 reviewer、等级、完整/部分范围、接受风险、未覆盖范围、文件哈希、diff 指纹和时间。

审查状态使用以下最小结构，字段名与提交门禁保持一致：

```json
{
  "status": "passed",
  "conclusion": "passed",
  "reviewer": "code-reviewer",
  "tier": "T1",
  "scope": "full",
  "accepted_risks": [],
  "uncovered_scope": [],
  "reviewed_files": [],
  "reviewed_file_hashes": {},
  "diff_fingerprint": "",
  "reviewed_at": ""
}
```

部分审查不得写成最终通过；有条件通过必须记录接受风险及理由。不记录 Agent ID、查询流水；提交说明只通过下方待用户验证说明预览分支由 `code-committer` 生成。

### Step 7：待用户验证说明预览

仅在同时满足以下条件时执行：

- 本次审查为完整范围，结论为“通过”或“有条件通过”，且没有待修复的 Critical / Important。
- 开发计划、修复批次或当前验证状态表明，剩余未完成验证全部由用户执行，例如硬件、现场、账号、视觉或人工判断；不存在仍待 AI 执行的构建、测试或检查。
- 没有活动阻塞，当前代码与审查凭据指纹一致。

调用 `code-committer` 的说明预览模式，传入当前审查范围和实际差异；不执行 Git/SVN 操作，不写入提交状态或替代用户验证。先输出以下固定标记，再使用 `code-committer` 的 Changelog 和提交说明模板：

```markdown
## 待用户验证说明预览

> 当前状态：代码审查已完成，仍待用户验证。
> 说明用途：供后续手动上传或提交时预览。
> 限制：未执行 Git/SVN 操作；当前不可作为最终交付凭据。
```

代码变化、审查范围变化或用户验证失败后，该预览立即失效；修复后的新一轮完整审查再次满足条件时重新生成。条件不满足时不生成预览，按原流程进入验证、修复或阻塞。

## 报告模板

T2/T3 或用户要求归档时使用总控解析的 `code_review` 模板。报告先给出交付判断，再说明按功能组织的审查范围、确认问题、范围限制和后续处理；不使用无解释的文件清单代替范围说明。

无问题时明确写“未发现阻塞问题”。报告不保留 reviewer 原始候选、已驳回问题、Agent 信息或查询过程；驳回项只有会影响后续判断时才记录简短反证。T0/T1 无阻塞时不生成完整报告，只写审查状态和一句结论。

## 完成前自检

在输出结论或写入凭据前检查：

- 是否通过 `subagent` 启动独立 `code-reviewer`、prompt 要求其先加载角色 Skill，并等待完成通知后复核？没有由主 Agent 直接加载角色 Skill 或模拟通过。
- 审查范围是否明确，最终凭据是否覆盖全部待交付产品代码？
- Git 仓库存在嵌套项目时，范围是否按最近的 DevFlow 项目根限定，没有混入其他项目差异？
- 输入是否包含判断本次改动所需的需求、设计、验证和适用约束？
- 当前最终差异是否都能对照同层同类参考、权威类型和文件检查结果；缺失证据是否补查而非默认通过？
- 是否只注入相关约束，没有在 Skill 中硬编码项目或框架规则？
- 是否按事实复核候选问题，没有把 reviewer 标签直接当作修改授权？
- Suggestion、误报和待确认项是否没有进入自动修改？
- 有条件通过和部分审查是否分别记录接受风险与未覆盖范围？
- 审查状态是否绑定当前文件哈希和 diff 指纹？
- 归档报告是否使用固定模板，且以复核后的结论、范围、问题和处理路径支持读者判断？
- 剩余验证仅由用户执行时，是否在不改变验证状态和版本控制授权的前提下生成了待用户验证说明预览？
