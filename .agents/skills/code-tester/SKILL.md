# Code Tester - 验证

## 原则

所有代码必须验证，但不强制每个任务重复构建，也不强制每次生成测试报告。需求开发编码结束后执行一次与风险匹配的正式构建；用户自测、联调或系统测试期间的一批 Bug 逐项只做原失败场景及直接影响场景的针对性检查，不逐项正式构建。公共声明、接口或构建配置变化在交给联调方前至少构建受影响目标；用户明确要求、下一版本准备交付或准备提交时，再对累计最终代码做风险匹配的正式构建与回归。构建、测试与代码指纹绑定，可供提交门禁复用。

## 触发场景

- `code-reviewer` 结论为通过或有条件通过后。
- 用户要求构建、测试、验证或生成测试报告。
- 下一版本准备交付或准备提交，但构建或验证凭据缺失、失效时。

## 输入

| 输入 | 用途 |
|---|---|
| 开发计划或修复批次 | 确认任务、Bug 状态、原失败场景、验收标准和验证清单 |
| 需求规格、技术改造计划或影响面、详细设计 | 确认目标项、不变行为、契约设计、验证重点和运行时约束 |
| UI 原型/界面稿 | 涉及 UI 且已触发原型时确认交互与视觉依据 |
| code-reviewer 结果 | 确认审查结论、接受风险和需重点测试的风险点 |
| 代码变更文件 | 确定测试影响面和回归范围 |
| 本次交付的最终差异、任务文件格式依据 | 确认编码/格式检查只覆盖待交付的修改文本源文件，且结果对应当前内容 |

## 深度与归档

| 等级 | 验证 | 记录位置 |
|---|---|---|
| T0 | 最小静态/局部检查和核心路径 | 计划或完成摘要 |
| T1 | 目标构建、局部测试、关键边界场景 | 开发计划验证清单 |
| T2/T3 | 正式构建、契约/集成/回归及风险场景 | `docs/06-测试/<迭代ID>-测试报告.md` |

失败、复杂验证或用户明确要求时可提高报告级别。

交付后修复批次按本批次实际修改的最高风险选择验证深度，不因缺少新开发计划而降低深度。除等级外，还要按实际风险加深验证：

| 风险 | 至少增加的验证 |
|---|---|
| UI | 本次涉及的默认、加载、空、错误、禁用、成功状态和关键交互 |
| 数据迁移/持久化 | 旧数据、默认值、读写一致性、升级和回退 |
| 接口兼容 | 旧调用方、字段缺省、错误响应和版本兼容 |
| 线程/并发/异步 | 线程归属、竞态、取消、重复触发和资源释放 |
| 缓存 | 更新、失效、回源和一致性 |
| 聚合或跨模块风险 | 组合场景、联调和受影响旧功能回归 |

## 验证状态

`待验证 / 已通过 / 未通过 / 无法执行 / 待用户验收`，并记录执行方 `AI / 用户`。

AI 无法执行 UI、硬件、现场、账号或人工判断测试时，生成用户验收清单：

| 验证ID | 前置条件 | 操作步骤 | 期望结果 | 状态 |
|---|---|---|---|---|

将整体状态改为 `waiting_user_validation`。用户反馈后回写结果；未执行不得标记通过。用户明确接受未验证风险时才能标记 `completed_with_risk`。

## 构建凭据

正式构建成功后保存或在验证结果中记录：命令、目标、结果、代码/工作区指纹和时间。代码变化使凭据失效；纯文档变化不失效。提交阶段有有效凭据时不重复构建。交付前的文件编码/格式检查也须对应最终差异；后续代码改动使受影响文件的检查结果失效。

纯文档和纯资源变化可不构建。仅注释变化只有在验证阶段明确确认不改变构建输入时才可人工豁免；提交 hook 不自动解析注释。公共接口或声明、构建配置及行为代码变化至少构建受影响目标。

## 失败路由

- 实现错误：回 `bug-fixer` 或当前执行上下文。
- 需求歧义：回 `spec-analyzer`。
- 范围遗漏：回 `impact-analyzer`。
- UI 原型/界面稿缺失：回 `ui-designer`。
- 技术设计缺失：回 `design-writer`。
- 环境、权限、依赖、许可证、设备或外部服务：立即通知用户，不反复尝试配置。

## 工作流程

1. 根据需求等级、开发计划或修复批次的验证清单、代码变更和用户要求确定验证范围。交付后 Bug 批次以实际测试版本的交付基线为起点；交付或提交前排除用户原有无关修改，以累计最终差异确定待交付文件，不用逐轮修复清单代替。
2. 优先执行项目已有构建、测试、静态检查和最小可复现场景；不为报告完整而发明测试。
   计划选择 TDD 时，核对任务中的红、绿、重构记录，并在最终代码上重新运行选中的自动化 `VERIFY`；任务期绿灯不能替代交付前的最终验证。
3. 需要新增或修改自动化测试代码时，开发迭代返回 `dev-builder` 创建或更新 `TASK-xxx`；交付后修复批次返回 `bug-fixer` 更新对应 `BUG-xxx`，不为此补造开发计划。`code-tester` 不直接编辑生产或测试代码。
4. 失败时保留最小失败命令、输入、日志和复现步骤。
5. 按失败根因路由到实现、需求、影响面、UI、详细设计或环境问题。
6. 修复后只复测失败项和直接受影响场景；下一版本交付或提交前，再对累计最终代码做与风险匹配的正式验证。
7. 交付或提交前，对最终待交付的修改文本源文件核对任务结束时的文件检查结果；缺失或内容变化时，按已确认的目标编码、BOM、行尾逐文件运行 `.devflow/scripts/check-source-file.py`，并执行项目已有格式器的检查模式。只检查本次文件，不自动格式化全仓库；无法执行时记录具体文件、原因及未覆盖风险，不写成通过。
8. 核对独立审查和构建/回归凭据覆盖同一最终交付范围及当前代码；修复或格式调整改变代码后，重做受影响检查并使旧指纹凭据失效。批次交付时将最终门禁和残余问题写回修复批次文档，未实际交付不得关闭。AI 无法执行的用户验收项生成清单，状态改为 `waiting_user_validation`。

## 报告

独立报告只写结论、范围、结果、风险和失败/复测。结果必须标明执行方和证据来源，不写执行过程流水，不生成空章节。

T2/T3、失败分析复杂或用户要求归档时使用固定模板：

```markdown
# 测试报告

## 结论

通过 / 失败 / 待复现 / 待用户验收

## 测试范围

| 项 | 内容 |
|---|---|
| 需求项 | <REQ-xxx> |
| 执行方 | AI / 用户 |
| 范围 | <构建、自动化、手动场景或 —> |

## 测试结果

| 场景 | 命令/步骤 | 结果 | 证据 |
|---|---|---|---|

## 失败分析

| 失败项 | 最小复现 | 根因类型 | 路由 |
|---|---|---|---|
```

无失败时省略“失败分析”。AI 无法执行的场景生成用户验收清单，状态写“待用户验收”，不得写“通过”。

## 完成前自检

在写入验证通过、待用户验收或测试报告前执行。未通过项先补齐证据或改为待用户验收，不得把未执行项标记为通过。

- 验证深度是否匹配 T0/T1/T2/T3 和实际风险？
- UI、迁移、兼容、并发、缓存和跨模块风险是否触发对应加深验证？
- `TASK` 编码与 `VERIFY` 执行是否分开？
- 需要修改自动化测试代码时是否已路由 `dev-builder`，而非在本阶段直接改代码？
- AI 无法执行的项目是否标记为待用户验收，而非通过？
- 失败是否有最小复现和明确路由？
- 构建凭据是否与代码指纹绑定？
- 交付前编码/格式检查是否覆盖最终待交付的修改文本源文件，且审查、构建和回归凭据对应同一最终差异？
- 报告是否只保留结论、范围、结果、风险和证据？
