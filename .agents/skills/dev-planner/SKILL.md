# Dev Planner - 开发计划

## 定位

开发计划只回答“派发哪些任务、目前做到哪里、如何验证”。业务事实以需求规格为准，UI 原型/界面稿以 `ui-designer` 输出为准，技术方案以详细设计为准。

T0 通常不归档计划；跨会话或确需恢复时可创建极简计划。T1/T2/T3 归档计划，生成后“建议查阅”，不作为新的审批门。

## 文档准备

仅在生成或实质修改开发计划前读取适用项目文档规范，并按总控解析 `document` 领域约束（默认 `.devflow/constraints/document-req.md`）。恢复阶段已读取的约束可复用；新会话、新执行 Agent 或约束变化后重新读取。

## 进入条件

- 产品需求已确认；技术改造的目标、不变行为与验证方式明确。活动阻塞为零。
- 产品需求 T0/T1 简要影响已写回需求规格；技术改造 T0/T1 简要影响已完成；或 T2/T3 独立影响面已确认。
- T2/T3 详细设计已确认；触发 UI 设计时其产物已确认。

任一条件不满足时只记录阻塞，不生成可执行任务，不以计划内容替代缺失决策。

## 输入

| 输入 | 用途 |
|---|---|
| `docs/02-需求/<迭代ID>-需求规格.md` | 已确认范围和验收标准；已有迭代使用实际登记路径 |
| 需求规格中的简要影响结论 | T0/T1 的影响对象、局部风险和最小实现约束 |
| `docs/02-需求/<迭代ID>-影响面分析.md` | T2/T3 的闭合链路、关键路径、聚合风险和实现边界；已有迭代使用实际登记路径 |
| `docs/04-设计/需求设计/<迭代ID>-需求设计.md` | 技术契约、实现边界和验证重点 |
| `docs/04-设计/概要设计/<迭代ID>-概要设计.md` | 按需系统边界、端到端数据流、兼容及回退；已有等价文档用实际路径 |
| `docs/04-设计/接口契约/<迭代ID>-接口契约.md` | 存在独立通信边界时的共享接口、字段、错误、枚举和通知 |
| `docs/05-UI/原型/<迭代ID>/` | 涉及 UI 且已触发原型时的界面依据 |
| 代码基线 | 区分当前迭代和用户已有改动 |

没有 UI 原型必要性时不读取 UI 原型；跳过详细设计的工作项从影响面实现要点生成任务。技术改造不虚构需求规格或 `REQ`；T1 在现有任务目标、设计依据和验证项中表达目标、不变行为与验证基线，需求覆盖表以“技术目标”记录对应关系，不增加模板行列或确认门。

## 任务拆分

- 按可独立交付的行为拆分，不按文件、函数、类或工具数量拆分。
- 使用能够表达真实依赖和独立交付边界的最少任务，不预设任务数量或工时阈值。
- 多个工具接入同一事件处理逻辑通常合并为一个任务。
- 生产代码和自动化测试代码可作为 `TASK-xxx`；构建、审查、测试执行和用户验收属于 `VERIFY-xxx`。
- 已选择单元或其他自动化测试时，测试代码列为 `TASK-xxx`，对应执行列为 `VERIFY-xxx`；无需单元测试时保留替代验证，不创建空任务。
- 已选择 TDD 时，在相关 `TASK` 的设计依据中注明本次采用逐行为红、绿、重构；同一行为的测试代码与实现归入同一任务交替完成，不拆成先批量写测试、后集中实现的两个任务。验证项仍负责最终代码的测试执行；未选择时不自动启用。
- 已确认“公开声明先审”时，首个编码任务只产出头文件、IDL 或等价公开声明草案，另设用户评审 `VERIFY-xxx`；未通过前不得派发转换、后端或 UI 实现任务。普通 REST 变化不触发此节点。
- T2/T3 任务引用详细设计章节，不复制技术细节；T0/T1 只保留一句最小实现约束。
- 任务目标只写可交付行为，不增加内容摘要、实现步骤、字段/枚举/消息清单或预计关键文件；实际修改文件和局部检查在完成后写入恢复信息。

## 基线

创建计划时记录：

- 基线标识：Git commit、SVN revision，或无版本控制时的文件快照/哈希。
- 初始工作区状态。
- 初始修改文件。

基线变化不自动阻塞；只有目标代码事实或契约变化时才重新检查影响面。用户原有修改不得自动纳入或回退。

## 工作流程

1. 检查进入条件。任一前置文档未确认或活动阻塞未清零时，只记录阻塞，不生成可执行任务。
2. 根据 Git、SVN 或无版本控制模式记录基线标识、初始工作区状态和初始修改文件，用于区分本次迭代与用户已有改动。
3. 从需求、影响面、UI 原型/界面稿、按需概要设计、需求设计、接口契约和验证设计中提取任务输入，只引用章节和最小约束，不复制技术细节。将节点的最终启用或跳过理由、完成证据与跳过风险的替代验证写入现有计划；入口建议不得未经影响分析直接当作定稿。
4. 按可独立交付行为生成 `TASK-xxx`；同一事件处理、重复工具接入和连续同模块修改优先合并。
5. 将构建、测试、审查、用户验收和手动场景列入 `VERIFY-xxx`，不混入编码任务。
   测试设计中的每个选中自动化入口应有测试代码任务及执行验证项；集成、系统或人工用例可直接对应验证项。公开声明先审时，声明草案评审是后续实现任务的执行前提。
6. 建立需求到任务、验证项的覆盖对照；没有编码任务的需求必须说明由哪个验证项覆盖或为何无需实施。
7. 区分任务内部依赖与外部依赖；外部团队、SDK、设备、环境、权限或协议未就绪时写入外部依赖，实际阻塞当前执行时再同步写入当前阻塞。
8. 写入计划整体的执行状态，并为任务和验证项预留恢复信息与证据，使中断恢复时能知道实际修改与验证到哪里；不记录时间线或 Agent 流水。
9. 输出前检查任务数量、粒度、依赖、需求覆盖、验证覆盖和恢复状态。

## 模板

使用总控解析的 `development_plan` 模板（默认 `references/开发计划_模板.md`）写入；无关配置警告不阻断，本模板不可读取或语义有疑问时提示用户处理，不自行改用默认模板：

```text
docs/08-计划/<迭代ID>-开发计划.md
```

默认模板严格保留其大纲和表格列，不自行增加“内容摘要、关键文件、实现步骤、工时、Agent”等字段；用户注入模板的结构按总控冲突确认结果执行。计划整体的`执行状态`只保存当前执行快照；任务的`恢复信息`只保存恢复所需的最新事实，例如实际修改文件、短结果、局部检查或阻塞原因；验证的`证据`只保存实际执行方式、结果和证据位置。需求到验证项的映射只维护在“需求覆盖”章节，不在验证计划重复。

计划整体、编码任务和验证项是不同状态层级：计划整体可使用“等待用户、已取消”，`TASK-xxx` 固定使用“待执行 / 执行中 / 已完成 / 阻塞 / 跳过”，`VERIFY-xxx` 使用上方验证状态。不同层级枚举不要求相同，也不得互相写入。

## 更新规则

只维护当前状态和恢复信息。任务开始时更新计划整体执行状态和任务状态；完成、阻塞或跳过时立即回写状态、恢复信息和必要证据。验证后回写状态与证据；版本控制存在时由其保存历史，没有时由基线、执行状态和恢复信息支持恢复。主要内容改变时同步 `progress.json` 的当前任务和里程碑。

## 完成前自检

在标记计划可执行或写入“建议查阅”前执行。未通过项先修正；前置文档未确认或活动阻塞未清零时，只记录阻塞。

- 计划是否只回答任务、状态、依赖、验证和阻塞？
- 是否没有复制需求事实、详细技术设计或 UI 原型内容？
- 是否严格使用固定大纲和表格列，并将文档边界、执行状态、开发任务、验证计划、需求覆盖、外部依赖和活动阻塞分开记录？
- 是否没有内容摘要、预计关键文件或实现步骤，且需求到验证项的映射未在验证计划重复？
- `TASK-xxx` 是否都是编码或必要技术产物，`VERIFY-xxx` 是否都是执行性验证？
- 是否避免按文件、函数、类或工具数量过细拆分？
- 是否记录基线、初始工作区和初始修改文件？
- 每个需求项是否都有对应任务和验证项，或明确记录无需编码的覆盖结论？
- 按需节点的启用、跳过理由和完成证据是否可从计划恢复；选中测试用例是否有对应的 `TASK/VERIFY`，且公开声明先审不会被后续任务越过？
- 外部依赖与任务依赖是否分开，当前未就绪且影响执行的事项是否进入阻塞？
- 计划整体是否具有当前执行状态，任务和验证项是否具有恢复所需的恢复信息或证据字段？
- 是否区分计划整体、`TASK-xxx` 和 `VERIFY-xxx` 三类状态，没有混用枚举？
- 是否没有时间线、Agent 名称/ID 和状态变化历史？
