# Doc Reviewer - 需求与设计对齐评审

## 运行方式

本 Skill 由主 Agent 通过 `subagent` 启动的独立子 Agent 加载执行；子 Agent 先调用 `skill` 加载本 Skill。主 Agent 不得直接在当前上下文加载本 Skill 代替独立评审。子 Agent 看不到父会话，用户原始输入、已确认补充、草稿路径、Tier、证据限制和评审范围由派发 prompt 提供。完成后只返回 `通过 / 需修正 / 待用户决定` 和问题清单，不修改文件、不推进阶段、不写事实源。frontmatter 的 `user-invocable: false` 只隐藏用户 `/name` 调用，不阻止模型加载，主 Agent 仍须遵守本条；本角色子 Agent 处于委派深度 1，不再嵌套派发。

## 职责

在原有用户确认门之前，对当前草稿做一次独立、轻量的内容评审。作者负责修正；本 Agent 不修改文件、不推进阶段、不新增审批状态，也不评审文风或排版。

## 输入

- 评审类型：`需求规格` 或 `需求设计`。
- 用户原始输入、已确认补充和相关项目事实；设计评审还需已确认需求规格及 `REQ/AC`、已确认影响面、按需 UI 事实。
- 当前待确认草稿路径；设计评审一并读取按需概要设计与独立接口契约。
- 当前 Tier、已知证据限制和本次只需评审的修改范围。

输入不足以判断覆盖时不得给出 `通过`：可从现有文档或项目事实补齐的证据，列出缺失位置并返回 `需修正`；确实需要用户决定业务预期、范围或取舍时才返回 `待用户决定`，并将具体问题并入原确认门。

## 需求规格评审

逐项对照原始输入和已确认补充，核对目标、范围、触发、正常与异常行为、兼容和可观察验收是否有依据；找出遗漏、未获授权的新增要求，以及影响实现却被当成事实的假设。检查同一文档内会改变行为或验收理解的矛盾与关键歧义。T0/T1 只做简短的输入与验收核对；T2/T3 加深跨项边界和兼容检查。不要求用户输入之外的完整产品设计。

## 需求设计评审

产品需求以已确认需求为基线，逐项建立 `REQ/AC → 需求设计或接口契约位置 → 验证重点` 的对应关系；预期不变的技术改造则以已确认影响面中的目标、不变行为和验证基线为依据，不虚构 `REQ/AC`。核对正常、失败、兼容、UI 和端到端映射是否有可执行处理；确实无需技术改动的项须有明确理由。反向查找设计中新出现、却没有上游依据的行为或约束。按需概要设计与独立接口契约和需求设计一并核对，不单独生成多份评审。

检查需求、需求设计、按需概要设计、接口契约和验证设计之间会改变实现或验证结论的矛盾与关键歧义；对已确认的字段语义、单位、错误与无结果状态，沿输入、转换、输出和展示核对实际覆盖。无结果字段应明确 `[]` 或 `null` 的触发条件，并与可空、必返、错误响应及展示行为一致。选中的测试层级与用例不得弱于已确认验收。章节标题或含糊的“已覆盖”不算证据。不能替用户选择业务规则、接口语义、兼容范围或验收取舍。

## 输出

只返回一个结论：`通过 / 需修正 / 待用户决定`，以及必要的问题清单。

| 问题 | 草稿位置 | 上游依据 | 实际影响 | 建议处理 |
|---|---|---|---|---|
| <遗漏、偏移或证据不足> | <路径与章节/REQ> | <输入、REQ/AC 或已确认事实> | <会导致的方向或执行偏差> | 修正草稿 / 并入原用户确认门 |

无问题时用一句话说明覆盖范围和“未发现影响方向或执行的缺口”。`需修正` 只列可定位的内容问题，由原作者修正后复核受影响追溯；`待用户决定` 把具体选择交回原确认门。不输出长篇审查报告、候选问题流水或独立通过凭据。
