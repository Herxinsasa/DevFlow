# Test Designer - 验证设计

## 定位与触发

本 Skill 只负责测试层级选择和用例设计，不独自构成 TDD 执行。T3 必须有测试层级选择及理由，单元测试仍可不启用；T2 的关键逻辑、复杂映射或高回归风险建议调用；T0/T1 默认复用现有验证，用户可要求提高深度。不调用本 Skill 时，`design-writer` 或 `dev-planner` 仍须说明对应风险由哪些验证覆盖。

## 输入与时机

- 已确认需求及 `REQ/AC`、影响面、按需 UI 事实和接口契约，以及需求设计草稿；技术改造使用已确认目标、不变行为和验证基线。
- 项目已有测试入口、替身能力、设备与环境约束。
- T2/T3 在设计和契约形成草稿后、原设计确认前执行；原设计确认前由主 Agent 通过 `subagent` 派发 `doc-reviewer` 做最终评审。不生成详设的工作项，在开发计划形成时记录验证依据。

## 工作方式

1. 从每个关键 `REQ/AC`、转换映射、错误、兼容和高风险边界提取可观察结果；没有依据的测试期望先返回上游澄清。
2. 为风险选择单元、集成、系统或人工层级及具体入口。优先用能稳定判断行为的最小层级；必须跨进程、设备或 UI 才能判断的行为选相应层级，不为凑单元测试检查私有实现形状。
3. 对选中的用例记录输入与边界、可观察断言、环境或替身、执行方。覆盖正常、边界、失败和兼容中实际相关的场景；说明无法自动化的原因和替代验证。
4. 有详设时写回需求设计的“验证设计”节；无详设时写入开发计划“验证计划”中的按需验证依据。引用已存在的需求和契约，不另建测试设计文档或确认门。
5. 交给 `dev-planner`：自动化测试代码归入 `TASK-xxx`，执行与结果作为 `VERIFY-xxx`。若选择 TDD，计划明确标注，并把对应测试和实现放在同一行为任务中，由 `dev-builder` 通过 `subagent` 派发 `implementer` 逐个行为执行红、绿、重构，不预先批量完成测试代码；本 Skill 不声称红灯或绿灯已经发生。未采用 TDD 时测试代码可随实现编写，但交付前必须运行所选验证。编码发现真实新边界时补充用例；不能为迎合实现删弱已确认断言。

## 用例最小结构

| 关联需求或风险 | 测试层级与入口 | 输入与边界 | 可观察断言 | 环境或替身 | 执行方 |
|---|---|---|---|---|---|
| REQ-001 / AC-001 | 单元 / 集成 / 系统 / 人工；<入口> | <场景> | <结果> | <已有设施或限制> | AI / 用户 |

完成前核对：测试期望是否来自已确认事实，测试层级选择是否有理由，关键风险是否有执行入口；跳过单元测试时是否明确替代验证；用例是否能映射到后续 `TASK/VERIFY`。
