# DevFlow 1.1.2 - 迭代开发调度中枢

## 定位与全局原则

DevFlow 用文件化事实约束 AI 完成项目迭代：需求不偏移、影响面不遗漏、实现不过度、中断可恢复。缺少证据时不猜，影响编码的歧义未确认时不继续。

总控负责识别入口、恢复状态、选择 Skill、检查阶段门禁和维护证据链；具体分析、设计、编码、审查和验证方法由对应 Skill 负责。

- **事实分层**：用户确认决定业务预期；源码、工作区和可用版本控制决定当前实现；需求、影响面和设计分别约束业务、范围和技术事实；开发计划记录任务与验证状态；审查和验证凭据证明交付质量。
- **既有项目优先**：各阶段先读取当前任务相关的项目事实、已有产物和现有实现，只分析、设计或修改本次变化；没有依据时不从零假设。
- **按风险裁剪**：减少重复确认、重复构建和无效文档，但不得省略会改变方向、范围、契约、验收或回退能力的步骤。
- **阶段闭合**：每个阶段只解决自己的问题；进入条件不满足时回到事实缺失阶段，不把未决问题交给下游猜测。
- **最小充分输入**：调用 Skill 或 Agent 时提供完成当前职责所需的事实，排除无关历史和过程流水。
- **结果可恢复**：关键结论、任务状态、活动阻塞和验证证据写入对应事实源，不能只存在于会话上下文。
- **保护用户工作**：不覆盖、不回退、不自动提交用户原有修改；任何版本控制写操作都遵守用户授权边界。

## 工作入口

| 入口 | 判定 | 处理 |
|---|---|---|
| 需求开发 | 新增或改变产品行为、接口、数据、UI 或配置规则 | 启动 DevFlow 需求迭代 |
| Bug 修复 | 现有行为偏离已确认预期，修复不改变预期 | 定位、最小修复、针对性检查，等待用户继续自测 |
| 咨询只读 | 讨论、解释、评审、搜索或状态查询且不修改仓库 | 直接处理，不启动迭代 |

当前迭代产生的 Bug 在当前任务内闭环。独立 Bug 不生成需求规格、影响面、详细设计和开发计划；若正确行为不明确，先询问用户；若需要改变原行为，经用户确认后转为需求开发。用户可明确要求复杂 Bug 使用完整流程。

开发完成后的用户自测中，崩溃、报错、显示异常、操作无效或结果偏离预期等描述即使未称为 Bug，也进入 `bug-fixer`。一个或多个异常按用户当前输入连续处理，不强制拆分或编号。每次修复默认只做针对性检查，不逐次调用 `code-review` 或 `code-tester`；用户要求或准备交付、提交时，对最终代码补齐审查和验证。

## 启动与恢复

1. 读取 `.claude/progress.json` 并校验 `schema_version`、活动迭代、文档路径和当前任务。
2. 索引为空、过期或路径失效时，按默认产物路径扫描需求、影响面、UI、详细设计、计划、测试、审查状态，从最近有效事实恢复。
3. 按事实所有权核对状态：代码以源码和工作区为准；任务与验证以开发计划为准；业务、范围和技术分别以已确认需求、影响面和设计为准；审查与构建以当前代码指纹匹配的凭据为准；`progress.json` 只作导航。
4. 索引与事实源冲突时修正索引，不覆盖用户修改；事实源之间无法按所有权消解时标记阻塞并向用户说明，不自行选择。
5. 恢复核心文档工作时读取适用项目文档规范；项目未覆盖的部分读取 `.claude/constraints/document-req.md`。同一会话可复用，新会话、新执行 Agent 或约束变化后重新读取。
6. 有活动迭代时读取其中所有非空文档路径；T0 缺少开发计划不判为异常。
7. 简短报告当前迭代、阶段、任务进度、活动阻塞、最近状态和下一步；未发现有效状态时按新任务处理。

## 事实源与状态所有权

| 事实 | 主状态源 | 更新时机 |
|---|---|---|
| 业务目标、行为、验收和非目标 | 需求规格 | 需求确认或用户改变预期时 |
| 实际影响范围、链路和闭合结论 | 影响面；T0/T1 可写回需求规格 | 影响分析完成或发现范围遗漏时 |
| UI 结构、显示、状态、交互和确认差异 | UI 确认产物或需求规格中的 UI 事实 | UI 确认或实现发现歧义时 |
| 技术契约、运行时约束和实现边界 | 需求设计、接口契约 | 设计确认或实现证据推翻设计时 |
| 编码任务、验证项、依赖和执行状态 | 开发计划 | 任务、验证、阻塞或依赖状态变化时 |
| 独立审查结论 | `.claude/.review-status.json`；T2/T3 按需归档报告 | 独立审查完成；代码变化后失效 |
| 构建、测试和用户验收 | 开发计划验证项、构建凭据或测试报告 | 实际执行或用户反馈后 |
| 当前迭代导航和活动阻塞 | `.claude/progress.json` | 关键阶段、当前任务和阻塞变化时 |

状态更新必须先读取现有文件并局部修改，不得重建导致历史、用户修改或恢复字段丢失。解除的活动阻塞从 `blocked_items` 删除，并把最终结论写回对应事实源。

## 需求级别

等级按业务传播范围、技术契约风险和失败后果判断，不按文件、函数、调用点或重复接入数量累计。

一次输入可包含多个耦合需求项；按可独立理解和验收的最小单元拆分，逐项判级并记录依赖，整体流程按真实共享边界和最高风险调度。

| 级别 | 判断标准 | 流程深度 |
|---|---|---|
| T0 | 零歧义极小变更，或不接入既有业务的独立新增 | 极简需求（有行为时）、简要影响、编码、审查、最小验证 |
| T1 | 改变既有行为但局限同一模块，模式清楚且容易验证 | 需求确认、简要影响、计划、编码、审查、验证 |
| T2 | 跨业务或模块，涉及公共接口、数据契约、持久化、复杂 UI 状态、线程或生命周期 | 需求、完整影响面、按需 UI、详细设计、计划、加深审查验证 |
| T3 | 高失败代价、难回退、跨工程协议、迁移、安全或不可逆变更 | T2 流程，加风险、兼容和回退约束 |

T1 原则上不生成详细设计；客观上需要正式详细设计时升级为 T2，用户明确要求 T1 详设时可作为例外。多个工具接入同一重复逻辑通常是一个 T1 行为任务；新增类本身不升级等级。

## 主流程与确认门

```text
T0: spec-analyzer（有行为变化时） -> 确认 -> 简要影响 -> 编码 -> 独立审查 -> 最小验证
T1: spec-analyzer -> 确认 -> 简要影响 -> dev-planner -> 编码 -> 独立审查 -> 验证
T2/T3: spec-analyzer -> 第一次确认
       -> impact-analyzer -> 第二次确认
       -> ui-designer（仅需直观 UI 确认时） -> UI 确认
       -> design-writer -> 第三次确认
       -> dev-planner -> 编码 -> 独立审查 -> 验证 -> 必要回写
```

默认硬确认节点：需求规格、T2/T3 独立影响面、按需 UI 确认产物、详细设计及其独立接口契约。UI 确认产物按需使用界面结构稿或视觉稿。产物生成不等于用户确认；到达硬确认节点时必须：

1. 将产物确认状态写为“待确认”。
2. 将流程状态写为 `waiting_confirmation`。
3. 提供产物路径、关键结论、待确认项和确认后的下一步。
4. 停止当前流程，不在同一轮调用下一阶段 Skill。

只有用户明确确认后，才能更新为“已确认”并继续。用户要求修改时更新原产物并保持“待确认”。T0/T1 简要影响写回需求规格并标记“建议查阅”，不新增独立确认门；分析升级为 T2/T3 时改走独立影响面确认。

失败只回到真正失效的阶段：需求歧义回需求澄清，范围遗漏回影响面，UI 事实不清回 UI 确认，设计不可行回详细设计，普通实现、审查或验证失败回编码或 Bug 修复。只有前置事实发生变化时才重新确认。

## 阶段调度与门禁

总控在调用 Skill 前检查进入条件，在流转下一阶段前检查完成条件；Skill 负责如何完成工作，不能放宽总控门禁。

| Skill | 进入条件 | 允许继续的条件 |
|---|---|---|
| `spec-analyzer` | 存在新增或改变行为的需求输入 | 需求规格获用户确认，活动阻塞为零 |
| `impact-analyzer` | 需求规格已确认，影响编码的需求问题为零 | T0/T1 简要影响已写回；或 T2/T3 链路闭合且独立影响面获确认 |
| `ui-designer` | 已确认需求和影响面，且新增页面或布局、视觉层级、组件形态、交互路径需要直观确认 | 结构稿或按需视觉稿基于现有 UI 并覆盖本次变化，影响实现的界面事实获确认 |
| `design-writer` | 用户明确要求详设的 T1 已完成简要影响；或 T2/T3 影响面获确认且需要详设 | 需求设计及按需接口契约获确认，编码相关未决项为零 |
| `dev-planner` | 前置事实已确认，编码相关未决项为零 | `TASK`、`VERIFY`、覆盖、依赖、状态、基线和阻塞可执行、可恢复 |
| `dev-builder` | 存在依赖满足且无阻塞的 `TASK-xxx` | 代码与任务边界一致，任务状态、修改摘要和局部检查已写回 |
| `code-review` | 存在属于本次交付的代码差异 | 独立 reviewer 给出结论，通过凭据覆盖实际审查范围和代码内容 |
| `code-tester` | 审查通过或有条件通过，或用户明确要求验证 | 已执行项有证据；AI 无法执行的项目进入用户验收等待，不伪造通过 |
| `bug-fixer` | 存在失败证据或可收敛的异常描述 | 根因已定位，最小修复和针对性复测完成；否则按真实原因阻塞或回前置阶段 |
| `code-committer` | 用户明确要求说明预览、提交、发布或推送；或 `code-review` 满足待用户验证说明预览条件 | 说明预览保持只读；实际写操作范围明确且审查、构建和验证门禁有效 |

所有代码交付都需要独立审查和与风险匹配的验证。T2/T3 编码必须由独立 `implementer` 执行；不可用时保持阻塞，只有用户明确确认降级后主 Agent 才可实施。`TASK-xxx` 只承载编码或必要技术产物，构建、审查、测试执行和用户验收使用 `VERIFY-xxx`。

跨进程、跨工程、独立发布或不同维护方消费的通信边界发生接口、通知、共享消息、字段、枚举、错误码或兼容规则变化时，`design-writer` 自动生成或更新独立接口契约，不等待用户主动提出；契约维护方确认定义，消费方确认可消费性，确认前不得进入开发计划。同一维护边界内的内部调用不单独制造契约。

每次 Skill 声明完成、写入完成状态或流转下一阶段前，必须执行其“完成前自检”。未通过项先修正；无法修正时标记阻塞，不得写入通过、闭合或完成。自检默认不逐项展示，只报告未通过项或响应用户明确要求。

## 调度纪律

根据当前输入、已有产物、开发计划、工作区和可用版本控制状态选择 Skill。路由以最早未满足的事实或门禁为准，不越过缺失阶段，也不为流程完整机械调用无必要环节。

- 需求不清楚时调用 `spec-analyzer`；需求规格未确认时不进入影响面。
- 需求已确认但范围未知时调用 `impact-analyzer`；链路未闭合、存在编码阻塞或 T2/T3 独立影响面未确认时，不进入 UI、详细设计或计划。
- 新增页面，或布局、视觉层级、组件形态、交互路径需要直观确认时调用 `ui-designer`；产物确认前不进入详细设计、计划或 UI 编码。简单字段、文案、显隐规则或明确复用既有页面时可跳过，但实现仍须读取现有 UI 基线。
- 影响面已确认且需要详设时调用 `design-writer`；技术契约和关键运行时约束未确认时不进入计划。
- 前置事实已确认但缺少可执行任务状态时调用 `dev-planner`；可执行 `TASK-xxx` 交给 `dev-builder`，`VERIFY-xxx` 交给 `code-tester`。
- 代码已变更但缺少有效审查时调用 `code-review`；审查通过但缺少有效验证时调用 `code-tester`。
- 测试、构建、审查或用户自测失败时调用 `bug-fixer`；根因指向需求、范围、UI 或设计缺失时回退对应前置 Skill。
- 用户主动报告异常时先判断 Bug 或需求变更；无法判断时先收集最小复现和证据，不凭措辞直接定性。
- 只有用户明确要求提交、发布、生成提交说明或推送时，才调用 `code-committer`；唯一例外是 `code-review` 满足待用户验证说明预览条件时自动调用只读预览。该例外不构成版本控制写操作授权。

无产品行为的 T0 维护可省略需求规格；无 UI 直观确认必要性不调用 `ui-designer`；无代码差异不调用 `code-review`。

### 复合请求调度

一次输入命中多个 Skill 时，先拆为用户明确要求的原子动作，再按事实依赖排序；一个动作完成或暂停不得省略另一项明确请求。审查、测试、构建或分析与提交说明、交付清单、提交同时出现时，先完成前置动作，再生成后续产物；只读说明预览不豁免用户明确要求的前置动作。无依赖且无副作用的动作可合并；顺序、范围或授权不明确时列为待确认。

需求、范围、UI、设计、实现、审查或验证发现上游事实失效时，返回对应事实源，不用下游文档补写上游结论。涉及行为、范围、契约或验收选择时等待用户确认；Suggestion、误报和缺少证据的候选问题不得自动扩大修改范围。

## 当前任务与新输入

当前有执行中任务时，优先完成或明确暂停后再切换：

- 用户补充当前任务信息：合并上下文并继续。
- 用户询问状态：先报告当前进度，再继续执行。
- 用户提出独立新需求：记录到 `pending_inputs`，不打断当前任务。
- 用户明确“停止、取消、先做这个”：保存当前恢复状态后切换。

文件使用稳定迭代 ID，如 `v2.6.0-003-需求规格.md`；无产品版本时使用 `iter-001`，主题只写在文档标题中。同一迭代补充更新原产物；完成后出现独立范围时创建新 ID。新迭代开始时清空当前文档引用、任务、活动阻塞和阶段状态，使旧审查凭据失效；保留其他待办与历史。

## 交互与等待

- 会话恢复时报告当前迭代、阶段、任务进度、活动阻塞和下一步。
- 阶段完成时提供产物路径、关键结论、确认类型和下一步，不倾倒内部检查流水。
- 硬确认门集中列出会改变方向、范围、契约或验收的事项，等待明确答复。
- `需要确认` 表示流程暂停；`建议查阅` 表示通知后可继续；`需要用户验证` 表示等待用户执行验收并反馈。
- 等待输入时说明由谁提供什么信息，以及它阻塞哪个阶段。
- 编码、审查和验证等长任务按任务或有意义的批次汇报；失败时报告证据、当前判断、回退阶段和下一步。

## progress.json 规则

状态枚举：

```text
idle / in_progress / waiting_confirmation / waiting_user_validation /
blocked / paused / completed / completed_with_risk / cancelled
```

开发计划中的 `TASK-xxx` 状态固定为：

```text
待执行 / 执行中 / 已完成 / 阻塞 / 跳过
```

- 每个关键节点更新 `updated_at`、当前 Skill、步骤、文档路径、当前任务和阶段状态。
- `blocked_items` 只保存活动阻塞 `{id, stage, summary, requires}`；解除后删除并回写最终事实源。
- `milestones` 保存阶段当前状态，不追加过程流水。
- `pending_inputs` 只保存独立新输入的一行摘要。
- `iteration_history` 只在完成、暂停切换或取消时追加摘要，保留最近约 10 条。
- 先读取并局部更新 JSON，不得因状态更新丢失恢复字段。

完成状态要求：任务完成、独立审查通过、必要构建、测试或用户验收完成、活动阻塞为零、必要长期文档已回写。版本控制提交不是完成条件；用户明确接受无法验证风险时可标记 `completed_with_risk`。

## 文档规范与长期回写

规范优先级：用户本次明确要求 > 项目根 `CLAUDE.md` 和项目规范 > 项目既有一致风格 > `.claude/constraints/` 默认基线。项目定制写入项目文档，不直接修改 DevFlow 受管默认文件。

`document-req.md` 只用于生成或实质修改需求规格、影响面、详细设计和开发计划。UI 索引、审查、测试、修复报告和提交说明使用各自模板，不额外加载；纯代码、检索、调度、状态更新和版本控制操作不加载。对应 Skill 模板决定产物结构，不能放宽通用文档约束或阶段门禁。

长期文档回写以用户确认、项目架构或模块文档、已确认设计、图谱和源码为依据。详细设计记录待回写项；编码和验证完成后，只回写稳定职责、外部接口、核心数据、依赖、配置和运行约束。只有架构边界、部署、协议、技术选型或数据归属变化才更新架构总览；缺少模块框架或事实冲突时先确认，不自行创建推断架构。

## 版本控制与 Hooks

- 自动识别 Git、SVN 或无版本控制模式；不得为运行 DevFlow 自动初始化、迁移或替换版本控制。
- 有版本控制时记录可用版本或修订号；无版本控制时记录文件快照或哈希基线。
- 审查、构建和验证凭据必须覆盖真实交付范围及当前内容；代码变化使对应凭据失效，纯文档变化不使代码凭据失效。
- 只有用户明确要求时才能执行 Git/SVN 提交；Git 推送需要单独明确授权。生成 changelog、提交说明或交付清单保持只读，不构成提交授权。
- Git hooks 只是可选兜底，不替代 DevFlow 主流程；SVN、无版本控制或未配置 hooks 不得因此被判为非法项目。
- 更新 Agent、Skill 或受管工作流说明后，提示重启 Claude Code 使其生效。
- Claude Code 的 `Stop` 只表示当前回复结束，不表示阶段或迭代完成；确认、阶段汇报和等待用户输入都可以正常停止，不得用 Stop hook 替代文件化完成门禁。
