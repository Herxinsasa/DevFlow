# Bug Fixer - 缺陷修复

## 入口

- 当前迭代的编译、测试、运行失败，或经复核确认的审查缺陷：在当前迭代内修复。Suggestion、被驳回问题和未确认的待确认项不得进入修复。
- 用户报告的独立 Bug：确认既有预期后直接定位、修复和针对性检查，完成后等待用户继续自测；不生成需求规格、影响面、详设或计划。
- 若正确预期需要改变，经用户确认转为需求开发。

## 铁律

不找出根因就不修复。没完成证据收集和最小复现，不能进入修复阶段；禁止看到报错就猜测性修改。

修复不得通过屏蔽错误、删除校验、放宽正确断言或修改测试去迎合错误实现来制造通过；不得扩大需求范围、夹带无关重构或用临时绕过替代根因修复。

## 上下文策略

原 implementer 或主 Agent 上下文仍在时直接修复。上下文已结束时只传递最小失败包：关联任务/需求、失败命令或步骤、错误摘要、复现性、当前 diff、允许范围和验收结果。仅在需要时读取更多文档。

根因未知、跨模块或运行时复杂问题才使用独立调试 Agent；普通局部失败不重复创建 Agent。

## 修复步骤

1. 收集原始错误、环境和最近变化，建立最小复现。
2. 形成可验证根因；不凭日志关键词猜改。
3. 判断根因属于实现、需求、影响面、UI 原型/界面稿、技术设计或环境。
4. 实现问题做最小修复并运行针对性复测。
5. 告知用户修复结果以及原审查、构建凭据已失效，然后等待继续自测；用户自测期间不逐次自动调用 `code-review` 或 `code-tester`。
6. 标记最终复审风险。修改接口、数据、配置、权限、复杂 UI 技术契约、多个模块，或修复原审查阻塞问题时，最终交付或提交前必须对相关变化增量复审；最终凭据仍须覆盖全部交付代码。

最小失败包至少包含：失败命令或操作、错误摘要、输入/配置、复现性、相关 diff、关联任务或需求、允许修改范围。无法稳定复现时先说明不确定性，不扩大修复。

## 重试上限

- 同一失败且代码、命令和环境未变化时最多重跑一次。
- 自动修复最多两轮；第三次仍失败时停止并通知用户，列出根因假设、已尝试修复和需要决定的事项。
- 不同错误只有在存在新证据和明确修复时继续，总尝试通常不超过三轮。
- 环境、权限、依赖、许可证、设备或外部服务问题首次识别即通知用户，不消耗修复轮次。

## 记录

用户自测期间的普通修复不逐项归档；最终验证时按需汇总结果。独立用户 Bug、生产事故或用户明确要求时才生成单独修复报告。记录只包含现象、根因、修复和复测结论。

需要单独归档时使用固定模板：

```markdown
# Bug 修复报告

## 结论

已修复 / 待补充设计 / 待补充需求 / 待复现

## 证据

| 项 | 内容 |
|---|---|

## 根因

| 类型 | 说明 | 证据 |
|---|---|---|

## 修复

| 文件 | 修改 | 原因 |
|---|---|---|

## 验证

| 验证项 | 结果 | 证据 |
|---|---|---|
```

无内容章节省略。普通自测 Bug 只在对话和最终验证汇总中说明，不追加过程流水。

## 完成前自检

在声明已修复、待复现、阻塞或返回用户继续自测前执行。未通过项先修正；正确行为不明确时回到需求确认，不扩大修复范围。

- 是否有原始错误和最小复现，或明确说明无法复现？
- 是否形成可验证根因，而不是看到报错就猜改？
- 修复是否最小，且没有扩大需求范围或做无关重构？
- 是否没有屏蔽错误、删除校验或修改测试去迎合错误实现？
- 针对性复测是否执行或说明无法执行原因？
- 是否正确判断需要回需求、影响面、UI 或详细设计？
- 是否告知用户原审查和构建凭据已失效？
- 涉及接口、数据、配置、权限、复杂 UI、多模块或原审查问题时，是否记录最终增量复审要求？
