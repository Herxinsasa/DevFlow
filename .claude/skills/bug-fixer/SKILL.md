# Bug Fixer - 缺陷修复

## 入口

- 当前迭代由编译、测试或审查自动发现的失败：按当前任务修复。Suggestion、被驳回问题和未确认的待确认项不得进入修复。
- 用户主动报告的 Bug，包括开发中、联调中和交付后的异常描述：先分析预期、失败证据、根因、影响和验证方式，再按风险决定直接修复或事前确认。独立 Bug 不生成需求规格、影响面、详设或计划。
- 若正确预期需要改变，经用户确认转为需求开发。

## 铁律

不找出可验证的根因就不修复。先建立失败信号；无法稳定复现时说明限制，用其他可靠证据检验根因，禁止看到报错就猜测性修改。

用户明确要求先分析或先看方案，或者预期、根因、范围不清，或者修改涉及公共接口/契约、持久化和兼容、安全权限、并发生命周期、跨模块行为、难回退操作时，须先向用户说明诊断依据、拟修改范围、风险和复测方式，获明确确认后才修改相关代码、测试或配置。证据不足时保持待证据，不把猜测作为待批准方案。预期明确、根因有据、改动局部可回退且可针对性验证的低风险问题可直接修复，并在完成后报告分析结论。分析阶段可读取代码、日志和文档；可能改动项目或外部环境的诊断动作须先说明影响。

修复不得通过屏蔽错误、删除校验、放宽正确断言或修改测试去迎合错误实现来制造通过；不得扩大需求范围、夹带无关重构或用临时绕过替代根因修复。

## 上下文策略

内部自动发现的失败在原 implementer 或主 Agent 上下文仍在时直接修复。用户报告的问题无论上下文是否仍在，都先执行诊断与风险判定。上下文已结束时只传递最小失败包：关联任务/需求、失败命令或步骤、错误摘要、复现性、当前 diff、允许范围和验收结果。仅在需要时读取更多文档。

实际修改代码前，按总控的冲突确认与优先级规则加载用户注入约束、项目根 `CLAUDE.md`、项目/模块规范、目标目录既有一致风格，以及解析后的 `coding`、`logging` 领域约束（无配置时使用 `.claude/constraints/` 默认基线）。已有上下文可以复用，但不能因进入 Bug 修复而省略编码约束。

根因未知、跨模块或运行时复杂问题才使用独立调试 Agent；普通局部失败不重复创建 Agent。

## 交付后修复批次

每次用户输入 Bug 都走本 Skill 的诊断、判险、修复和局部复测；批次记录不是另一个修复步骤。初版代码已交付测试、开发任务已退出活动状态后，同一测试版本的多轮用户自测、联调和系统测试反馈归入一个逻辑批次。项目已有可恢复的版本问题清单或测试记录，且能保存下述问题与最终门禁信息时，直接复用并记录其项目内路径；否则默认建立 `docs/06-测试/<批次ID>-修复批次.md`，使用总控解析的 `repair_batch` 模板（默认 `references/修复批次_模板.md`）。无关配置警告不阻断修复；本模板不可读取或语义有疑问时提示用户选择修复方式，不自行改用默认模板。同一版本后续反馈更新同一记录，不因新一轮报告或重新开始会话另开批次。单个独立 Bug 不在持续测试批次中时，不强制生成批次文档；开发中未交付的自测问题仍留在原开发迭代。

批次基线取实际交付代码标识（Git commit、SVN revision 或文件快照），同时识别交付时已有的无关修改；目标是下一交付版本。开始批次时按总控的新迭代规则切换唯一 `current_iteration`，将原需求迭代的真实完成或暂停状态存入 `iteration_history`，清空当前任务和旧文档导航，在 `documents.repair_batch` 记所用项目内记录的路径。原迭代若还有未完成的开发任务，先解决状态冲突，不并行维护两个活动迭代；待用户验收不得伪写成完成。恢复时优先读批次记录、测试版本和交付基线，以当前代码重核累计差异。

每个问题分配稳定 `BUG-xxx`；记录现象与原预期、版本及失败信号、根因依据、风险与确认、最小修复、针对性复测和当前状态。相同根因的重复报告合并并保留原报告关联；证据不足写待证据，不写猜测性修复。每轮新报告重新分析；确需事前确认的项写入批次并使用既有 `waiting_confirmation` 导航，确认前不修改该项。新功能默认写入 `pending_inputs` 待批次交付后处理；若修复需要改变原预期，该问题标为转需求，其余 Bug 继续处理。

每项修复后只做针对性复测并更新批次记录，不逐项生成独立审查或正式构建。公共声明、接口或构建配置变化在交给联调方前至少构建受影响目标。下一版本交付或用户要求提交前，从交付基线和当前代码重新确定本批次累计最终差异，排除用户原有无关修改，对这份最终差异统一执行独立 `code-reviewer`、风险匹配构建及回归；结果和代码指纹写入批次最终门禁。代码改变后重核受影响凭据；未执行不得标记通过。目标版本实际交付且残余问题已处理或明确接受后，将批次记录标为已交付；`progress.json` 仍按实际验收状态结束或等待用户验收，不能仅因交付就写 `completed`。新反馈以已交付版本为基线建立新批次，切换时将上一批次真实状态存入历史。交付不自动授权提交或推送。

## 修复步骤

### A. 诊断与风险判定（用户报告时必经）

1. 收集原始描述、既有预期、版本和环境、最近变化，建立可重复或可判定的失败信号；诊断阶段不改生产代码、测试或配置。
2. 用代码、日志和复现证据检验根因，区分实现、需求、影响面、UI、技术设计和环境问题；不能复现或证据不足时列出需要的材料，不提出猜测性修复。
3. 逐项判定：只有预期明确、根因有据、改动局部可回退、验证可执行，且不涉及公共契约、持久化、安全、并发生命周期、跨模块行为等高风险边界，才进入直接修复。用户要求先看分析或方案时，即使低风险也进入确认分支。一次报告多个 Bug 可分流处理，不让待确认项阻塞无依赖的低风险项。
4. 确需确认的项向用户报告现象与预期、关键证据、根因及不确定性、拟修改范围、可能影响和复测方式；记录简短诊断，将相关项置为 `waiting_confirmation`，停止修改这些项。多项可合并请求确认，但逐项标明结论与范围；无依赖的低风险项仍可继续处理。补充现象或日志不算确认，用户不同意时继续分析。

### B. 最小修复与复测

1. 对符合直接修复条件、已获必要确认的用户报告问题，或当前任务内部自动发现的失败，按适用编码约束做最小修复。
2. 若修复中发现根因、行为预期或范围与风险判定或已确认结论实质不符，立即停下并返回 A；新增高风险边界或已确认方案实质变化时重新确认。未确认的问题不搭车修改。
3. 运行原失败场景和直接受影响场景的针对性复测，不能执行时说明原因。
4. 告知用户诊断、实际修改、复测证据、未覆盖场景和原审查/构建凭据是否失效；交付后批次同步更新当前 `BUG-xxx`，然后等待继续自测。联调或系统测试的一批 Bug 不逐项自动调用独立 `code-reviewer` 或 `code-tester` 做正式构建；用户明确要求时可提前执行。
5. 公共声明、接口或构建配置变化在交给联调方前至少构建受影响目标。下一版本交付或用户要求提交前，对累计最终差异统一做一次独立审查、风险匹配构建和回归；审查发现问题后的修正仅复核受影响部分，最终凭据仍须覆盖全部交付代码。

最小失败包至少包含：失败命令或操作、错误摘要、输入/配置、复现性、相关 diff、关联任务或需求、允许修改范围。无法稳定复现时先说明不确定性，不扩大修复。

## 重试上限

- 同一失败且代码、命令和环境未变化时最多重跑一次。
- 自动修复最多两轮；第三次仍失败时停止并通知用户，列出根因假设、已尝试修复和需要决定的事项。
- 不同错误只有在存在新证据和明确修复时继续，总尝试通常不超过三轮。
- 环境、权限、依赖、许可证、设备或外部服务问题首次识别即通知用户，不消耗修复轮次。

## 记录

用户自测期间的普通修复不逐项生成报告；逐项结论保存在当前计划或批次记录中，只有确需等待确认的项才在 `progress.json` 留导航摘要。交付后批次以批次文档为主，不再为每个 Bug 生成报告；独立用户 Bug、生产事故或用户明确要求时才生成单独修复报告。记录只包含现象、诊断与必要确认、根因、修复和复测结论。

需要单独归档时使用固定模板：

```markdown
# Bug 修复报告

## 结论

已修复 / 待补充设计 / 待补充需求 / 待复现

## 证据

| 项 | 内容 |
|---|---|

## 根因

| 类型 | 说明 | 证据 |
|---|---|---|

## 修复确认

| 诊断结论 | 拟改范围 | 风险及必要确认状态 |
|---|---|---|

## 修复

| 文件 | 修改 | 原因 |
|---|---|---|

## 验证

| 验证项 | 结果 | 证据 |
|---|---|---|
```

无内容章节省略。普通自测 Bug 不生成独立报告；等待确认的结论保留在当前事实源，修复结果在对话和最终验证中汇总，不追加过程流水。

## 完成前自检

在报告诊断、等待确认、声明已修复、待复现、阻塞或返回用户继续自测前执行。未通过项先修正；正确行为不明确时回到需求确认，不扩大修复范围。

- 是否有原始错误和最小复现，或明确说明无法复现？
- 是否形成可验证根因，而不是看到报错就猜改？
- 用户报告的问题是否都已先分析并判险；需事前确认的项是否在获明确确认前保持只读？
- 批量报告是否仅修复符合直接修复条件或已获必要确认的项；根因或范围实质变化时是否重新判险、必要时重新确认？
- 修复是否最小，且没有扩大需求范围或做无关重构？
- 实际修改前是否已加载适用编码约束和目标目录代表性代码？
- 是否没有屏蔽错误、删除校验或修改测试去迎合错误实现？
- 针对性复测是否执行或说明无法执行原因？
- 是否正确判断需要回需求、影响面、UI 或详细设计？
- 是否告知用户原审查和构建凭据的失效情况？
- 是否避免联调批次逐项独立评审和正式构建，并在公共声明/接口或构建配置交付联调前构建受影响目标？
- 下一版本交付或提交前，累计最终差异是否有统一独立审查、风险匹配构建和回归计划？
- 交付后反馈是否按测试版本复用唯一批次、稳定 `BUG-xxx` 和现有 `current_iteration`，没有把旧迭代或待用户验收误写为完成？
- 批次实际交付前是否重核累计最终差异、门禁及代码指纹；未交付时是否保持进行中或待交付？
