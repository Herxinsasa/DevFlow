# Code Committer - 提交辅助

## 操作模式

- **说明预览**：用户只要求 changelog 或 commit message。读取实际差异并生成文案，不要求审查、验证或构建凭据，也不执行 Git 写操作。
- **提交**：用户明确要求 commit。检查完整提交门禁，展示范围和文案，用户确认后才暂存并提交。
- **推送**：用户明确要求 push。先满足提交模式；只有推送目标和当前提交明确时才推送。

## 提交门禁

本节只约束实际提交或推送；说明预览不因凭据缺失而阻塞。

1. 计划存在时，目标任务完成且活动阻塞已说明；T0 无计划不因此阻塞。存在未完成、跳过或阻塞任务时，必须展示包含项、排除项和残余风险，并获得用户对部分提交的明确确认。
2. `.claude/.review-status.json` 结论通过，范围覆盖所有暂存代码，文件哈希/diff 指纹仍匹配。
3. 必要验证已通过；等待用户验收、失败或无法执行且未获风险接受时停止。
4. 构建凭据与当前代码指纹匹配；没有有效凭据时调用 hook 构建检查。
5. 暂存范围不包含用户无关修改、运行状态、日志、缓存或构建产物。

代码变化使审查和构建凭据失效；纯文档变化不使构建凭据失效。纯文档和纯资源变化可跳过构建；仅注释变化须有验证阶段的人工豁免记录，否则仍按源码变化处理。所有情况仍需核对审查范围。

提交时代码审查凭据缺失或失效，先执行 `code-review`；构建凭据缺失或失效，再执行正式构建。用户在自测期间选择暂不审查或编译只表示延后，不能作为代码提交豁免。

## 构建复用

测试阶段或提交前检查可写 `.claude/.build-status.json`：命令、目标、结果、指纹模式、代码指纹和时间。提交前凭据按暂存区计算；存在未暂存代码变化时停止构建，避免构建内容与提交内容不一致。`pre-commit-check.ps1` 匹配有效凭据时不重复构建，否则执行一次项目构建并更新凭据。

## 工作流程

1. 根据用户请求确定说明预览、提交或推送模式；不把“帮我写提交说明”解释成提交授权。
2. 检查 Git 状态、暂存区和未跟踪文件，列出可能误提交的日志、缓存、构建产物和用户无关修改。
3. 说明预览模式生成 changelog 和 commit message 后停止，并声明没有执行 Git 写操作。
4. 提交或推送模式检查任务状态、活动阻塞、审查、验证和构建凭据；不是完整迭代提交时，单独确认部分提交范围。
5. 凭据缺失或失效时，先路由到 `code-review`、`code-tester` 或构建检查，不绕过门禁。
6. 生成简洁 changelog 和 commit message，只写实际变更；验证结论放在提交前摘要，不塞入 commit message。
7. 展示提交范围、排除项和提交信息，用户确认后才执行 `git add` / `git commit`。
8. 只有用户明确要求 push 时才推送。

## 提交说明

先展示实际变更清单、简洁 changelog 和 commit message。两者只概括最终代码或文档发生了什么，不复述分析、讨论、审查和修复过程，也不堆叠文件路径与验证证据。

Changelog 模板：

```markdown
## Changelog

新增:
- <需求项 / 任务对应的新增能力>

删除:
- <现有文件/代码内容的删除>

修改:
- <需求项 / 任务对应的修改>
- <Bug 或测试失败修复>
```

Commit message 模板：

```text
【<项目名称>：<需求迭代编号>】
新增:
- ...
删除:
- ...
修改:
- ...
```

无内容的分类省略。每条使用动词开头，只表达一个“动作 + 对象”；默认保持一行，通常每类 1 至 3 条、整条 commit message 不超过 5 个要点。复杂变更需要更多要点时可以适当增加，不为满足字数机械删减关键信息。详细原因、链路、过程和验证证据留在文档、报告或提交前摘要中。

## 输出

- 说明预览：差异范围、changelog 和 commit message，并明确未执行 Git 写操作。
- 提交或推送：实际提交范围、排除项、审查/验证/构建凭据结论，以及用户授权的 Git 操作结果。

## 完成前自检

说明预览只检查差异来源和文案准确性。实际提交或推送时，生成提交说明前执行一次完整自检；用户确认后、写入 Git 前再按暂存区和凭据执行一次。未通过项先补齐审查、验证、构建或暂存范围，不得提交。

- 是否正确区分了说明预览、提交和推送授权？
- 实际提交时，存在未完成、跳过或阻塞任务是否已获得用户对包含项、排除项和残余风险的明确确认？
- 实际提交时，暂存范围是否排除了无关修改、缓存、日志和构建产物？
- 实际提交时，代码文件是否有覆盖当前暂存内容的审查凭据？
- 实际提交时，构建或验证凭据是否与当前代码指纹匹配？
- 实际提交时，是否存在未暂存代码导致构建内容与提交内容不一致？
- 实际提交是否经用户确认，且没有把提交授权扩大成 push 授权？
