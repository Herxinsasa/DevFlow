# Code Committer - 提交辅助

## 触发

仅用户明确要求提交、commit、发布、changelog 或 push 时触发。

## 提交门禁

1. 计划存在时，目标任务完成且活动阻塞已说明；T0 无计划不因此阻塞。存在未完成、跳过或阻塞任务时，必须展示包含项、排除项和残余风险，并获得用户对部分提交的明确确认。
2. `.claude/.review-status.json` 结论通过，范围覆盖所有暂存代码，文件哈希/diff 指纹仍匹配。
3. 必要验证已通过；等待用户验收、失败或无法执行且未获风险接受时停止。
4. 构建凭据与当前代码指纹匹配；没有有效凭据时调用 hook 构建检查。
5. 暂存范围不包含用户无关修改、运行状态、日志、缓存或构建产物。

代码变化使审查和构建凭据失效；纯文档变化不使构建凭据失效。纯文档和纯资源变化可跳过构建；仅注释变化须有验证阶段的人工豁免记录，否则仍按源码变化处理。所有情况仍需核对审查范围。

提交时代码审查凭据缺失或失效，先执行 `code-review`；构建凭据缺失或失效，再执行正式构建。用户在自测期间选择暂不审查或编译只表示延后，不能作为代码提交豁免。

## 构建复用

测试阶段或提交前检查可写 `.claude/.build-status.json`：命令、目标、结果、指纹模式、代码指纹和时间。提交前凭据按暂存区计算；存在未暂存代码变化时停止构建，避免构建内容与提交内容不一致。`pre-commit-check.ps1` 匹配有效凭据时不重复构建，否则执行一次项目构建并更新凭据。

## 工作流程

1. 确认用户明确要求提交、生成提交说明、发布或推送。
2. 检查 Git 状态、暂存区和未跟踪文件，列出可能误提交的日志、缓存、构建产物和用户无关修改。
3. 检查任务状态、活动阻塞、审查凭据、验证结果和构建凭据；不是完整迭代提交时，单独确认部分提交范围。
4. 凭据缺失或失效时，先路由到 `code-review`、`code-tester` 或构建检查，不绕过门禁。
5. 生成简洁 changelog 和 commit message，只写实际变更和验证结论。
6. 展示提交范围、排除项和提交信息，用户确认后才执行 `git add` / `git commit`。
7. 只有用户明确要求 push 时才推送。

## 提交内容

先展示实际变更清单、简洁 changelog 和 commit message。提交信息按实际变更写“新增/修改/修复/验证”，每条简短，不复述文档过程。用户确认后才执行 `git add` 和 `git commit`；只有明确要求才 push。

Changelog 模板：

```markdown
## Changelog

新增:
- <需求项 / 任务对应的新增能力>

删除:
- <现有文件/代码内容的删除>

修改:
- <需求项 / 任务对应的修改>
- <Bug 或测试失败修复>
```

Commit message 模板：

```text
【<项目名称>：<需求迭代编号>】
新增:
- ...
删除:
- ...
修改:
- ...
```

无内容的分类可省略。每条要点不超过 20 个中文字符，使用动词开头。详细原因、链路和过程写入文档或报告，不写入 commit message。

## 输出

- 实际提交范围和排除项。
- 审查、验证与构建凭据结论。
- changelog、commit message 和用户要求的 Git 操作结果。

## 完成前自检

生成提交说明前先执行一次；用户确认后、实际提交前再按暂存区和凭据执行一次。未通过项先补齐审查、验证、构建或暂存范围，不得提交。

- 是否由用户明确要求提交或推送？
- 存在未完成、跳过或阻塞任务时，是否获得用户对包含项、排除项和残余风险的明确确认？
- 暂存范围是否排除了无关修改、缓存、日志和构建产物？
- 代码文件是否有覆盖当前暂存内容的审查凭据？
- 构建或验证凭据是否与当前代码指纹匹配？
- 是否存在未暂存代码导致构建内容与提交内容不一致？
- 是否经用户确认后才提交，且没有默认 push？
