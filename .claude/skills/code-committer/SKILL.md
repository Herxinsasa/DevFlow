# Code Committer - 提交辅助

## 操作模式

- **说明预览**：用户明确要求 changelog 或提交说明，或由 `code-review` 的待用户验证分支自动路由。读取实际差异并生成文案，不要求审查、验证或构建凭据，也不执行版本控制写操作；该自动路由是唯一无需用户主动请求的只读例外，不授权暂存、提交或推送。同一输入还明确要求审查、测试、构建或分析时，先完成该动作，说明预览不得短路。
- **提交**：用户明确要求提交。Git 使用暂存区提交，SVN 使用明确选择的路径提交；检查完整门禁并再次确认范围后才执行。
- **推送**：只适用于 Git，且必须由用户明确要求；提交授权不自动包含推送授权。
- **无版本控制**：可以生成变更说明和交付文件清单，但不能声称已提交；若用户要求提交，说明当前目录没有可用版本控制并停止。

## 提交门禁

本节只约束实际提交或推送；说明预览不因凭据缺失而阻塞。先识别 Git、SVN 或无版本控制模式，不因缺少 Git 把有效 SVN/普通目录判为非法项目。

1. 计划存在时，目标任务完成且活动阻塞已说明；T0 无计划不因此阻塞。存在未完成、跳过或阻塞任务时，必须展示包含项、排除项和残余风险，并获得用户对部分提交的明确确认。
2. `.claude/.review-status.json` 结论通过，范围覆盖本次选择提交的全部代码，文件哈希和变更指纹仍匹配。
3. 必要验证已通过；等待用户验收、失败或无法执行且未获风险接受时停止。
4. 构建凭据与当前代码指纹匹配；没有有效凭据时调用 hook 构建检查。
5. 提交范围不包含用户无关修改、运行状态、日志、缓存或构建产物。

代码变化使审查和构建凭据失效；纯文档变化不使构建凭据失效。纯文档和纯资源变化可跳过构建；仅注释变化须有验证阶段的人工豁免记录，否则仍按源码变化处理。所有情况仍需核对审查范围。

提交时代码审查凭据缺失或失效，先执行 `code-review`；构建凭据缺失或失效，再执行正式构建。用户在自测期间选择暂不审查或编译只表示延后，不能作为代码提交豁免。

## 凭据复用

测试阶段或提交前检查可写 `.claude/.build-status.json`：命令、目标、结果、指纹模式、代码指纹和时间。Git 按暂存区计算提交指纹；SVN 按明确选择的提交路径计算；无版本控制时按交付文件清单计算。凭据范围与实际交付范围不一致时停止复用。Git 项目可由 `pre-commit-check.ps1` 兜底，SVN 和无版本控制项目由工作流在提交或交付前执行同等检查。

## 工作流程

1. 识别 Git、SVN 或无版本控制模式，将请求拆分为说明预览、提交、推送及用户明确要求的前置动作；存在审查、测试、构建或分析时，按依赖先完成前置动作，再处理说明预览、提交或推送。`code-review` 可以按待用户验证分支自动请求说明预览，除此之外无用户明确请求时不调用本 Skill；任何说明预览都不得解释成提交授权。
2. 使用当前模式可用的状态和差异能力检查变更，列出可能误交付的日志、缓存、构建产物和用户无关修改；无版本控制时使用迭代基线或明确文件清单。
3. 说明预览模式在没有未完成的明确前置动作时，生成 changelog 和提交说明后停止，并声明没有执行版本控制写操作。
4. 无版本控制目录收到提交请求时说明限制并停止；可以按用户要求改为生成交付清单或补丁，但不虚构提交结果。
5. Git/SVN 提交模式检查任务状态、活动阻塞、审查、验证和构建凭据；不是完整迭代提交时，单独确认部分提交范围。
6. 凭据缺失或失效时，先路由到 `code-review`、`code-tester` 或构建检查，不绕过门禁。
7. 生成简洁 changelog 和提交说明，只写实际变更；验证结论放在提交前摘要，不塞入提交说明。
8. 展示提交范围、排除项和提交信息，用户确认后才执行对应版本控制命令；SVN 必须显式传入选择的路径，避免提交整个工作副本的无关修改。
9. 只有用户明确要求且当前为 Git 时才推送。

## 提交说明

先展示实际变更清单、简洁 changelog 和提交说明。两者只概括最终代码或文档发生了什么，不复述分析、讨论、审查和修复过程，也不堆叠文件路径与验证证据。

Changelog 模板：

```markdown
## Changelog

新增:
- <需求项 / 任务对应的新增能力>

删除:
- <现有文件/代码内容的删除>

修改:
- <需求项 / 任务对应的修改>
- <Bug 或测试失败修复>
```

提交说明模板：

```text
【<项目名称>：<需求迭代编号>】
新增:
- ...
删除:
- ...
修改:
- ...
```

无内容的分类省略。每条使用动词开头，只表达一个“动作 + 对象”；默认保持一行，通常每类 1 至 3 条、整条提交说明不超过 5 个要点。复杂变更需要更多要点时可以适当增加，不为满足字数机械删减关键信息。详细原因、链路、过程和验证证据留在文档、报告或提交前摘要中。

## 输出

- 说明预览：差异范围、changelog 和提交说明，并明确未执行版本控制写操作。
- Git/SVN 提交：实际提交范围、排除项、审查/验证/构建凭据结论，以及用户授权的操作结果。
- 无版本控制：变更说明和交付文件清单，或无法提交的明确说明。

## 完成前自检

说明预览只检查差异来源和文案准确性。实际提交或推送时，生成提交说明前执行一次完整自检；用户确认后、写入版本控制前再按实际提交范围和凭据执行一次。未通过项先补齐审查、验证、构建或范围，不得提交。

- 是否正确区分了说明预览、提交和推送授权？
- 实际提交时，存在未完成、跳过或阻塞任务是否已获得用户对包含项、排除项和残余风险的明确确认？
- 实际提交时，选择范围是否排除了无关修改、缓存、日志和构建产物？
- 实际提交时，代码文件是否有覆盖当前选择内容的审查凭据？
- 实际提交时，构建或验证凭据是否与当前代码指纹匹配？
- 实际提交时，构建与审查凭据是否覆盖当前模式下的真实提交范围？
- 实际提交是否经用户确认；Git 提交授权是否没有被扩大成推送授权？
