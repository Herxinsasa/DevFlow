# Code Review - 独立代码审查

## 铁律

所有代码交付都需要独立审查。审查者不继承编码判断，不直接修改代码。不可用时不得写通过状态：T0/T1 可继续本地验证但不能提交，T2/T3 停止交付并通知用户。

## 触发场景

- `dev-builder` 完成关联任务后。
- 开发计划中所有可执行任务完成后。
- 用户说“审查代码”“code review”“看下这次改动风险”。
- 用户要求评审 Skill、Agent、Hook、模板或工作流规则的一致性。
- 准备提交但审查凭据缺失、失效或未覆盖当前代码时。

## 审查对象分类

审查前先分类，因为不同对象的事实源和严重程度判定不同：

| 类型 | 范围 | 主要事实源 | 审查重点 |
|---|---|---|---|
| 产品代码 | 业务源码、配置、构建文件、自动化测试 | 已确认需求、影响面、设计、项目规范和源码 | 功能、契约、范围、回归、安全与验证 |
| 工作流控制面 | `.claude/`、Skill、Agent、Hook、模板、工作流约束和说明 | 用户当前目标、当前 `CLAUDE.md`、Skill 职责边界、版本说明和实际文件 | 调度是否可执行、规则是否自洽、路径/状态/凭据是否真实 |
| 混合变更 | 同时包含产品代码与工作流控制面 | 分别使用对应事实源 | 分开列结论，不把工作流设计偏好当成产品缺陷 |

工作流文档会影响 Agent 行为，因此可以审查；但只有会导致错误路由、无效路径、门禁失效、状态不可恢复或确定性错误执行的矛盾，才可列为 Critical/Important。措辞偏好、可选目录组织和存在多种合理方案的设计取舍不能直接判为必须修复。

## 审查深度

- T0：快速核对 diff、需求/验收和项目规范；干净时只记录状态与一句结论。
- T1：核对需求一致性、修改范围、局部回归和验证充分性；干净时不强制独立报告。
- T2/T3：完整检查契约、数据、UI、运行时、安全、性能和回归，归档 `docs/07-审查/<迭代ID>-代码审查.md`。

关联任务完成后统一审查，避免逐任务重复；早期集成、高风险接口或分批交付可中途审查。用户自测期间的 Bug 修复不逐次触发审查，用户明确要求或准备提交时统一审查当前最终差异。审查问题修复后只增量复审相关变化，最终凭据必须覆盖全部提交代码。

## 输入

- 实际 Git diff、变更文件和初始工作区快照。
- 关联需求与验收标准。
- T2/T3 详细设计及按需 UI 原型/界面稿；T0/T1 简要影响和最小约束。
- 项目规范、局部验证结果和已知限制。

不依赖 Agent 执行流水。

没有 UI 原型必要性时不读取 UI 原型。审查范围以开发计划基线、迭代开始时已有变更、任务目标文件和实际 diff 共同确定，不把无法证明属于本次迭代的已有改动自动纳入通过结论。

## 工作流程

1. 检查 `code-reviewer` 是否可用。不可用时不得由主 Agent 模拟通过，也不得写审查凭据。
2. 分类审查对象并确定范围：默认审查当前最终差异；部分审查必须标明未覆盖范围。
3. 组装审查输入：对象类型、diff、变更文件、需求/设计依据、当前工作流事实源、UI 原型/界面稿、局部验证、项目规范和已知限制。
4. 派发独立 `code-reviewer`，要求发现优先输出候选问题，按严重程度排序，并为每项给出证据、影响和置信度。
5. 对候选问题做处置验真：核对当前事实源、文件语义和实际执行后果，不能把 reviewer 标签本身当作修改依据。
6. 输出处置结果。确认缺陷回编码或对应前置阶段；需要决策的问题暂停并请求用户确认；Suggestion 只记录；误报说明反证并驳回。
7. 修复后只增量复审相关变化；通过或有条件通过时写入审查状态，记录结论、接受风险、未覆盖范围、文件哈希和 diff 指纹。

审查输入应包含项目代码约定，至少包括字符集/BOM、行尾、命名、注释、日志和代表性样例文件路径。

## 结论

问题按 Critical、Important、Suggestion 排序。只有经证据验真的 Critical/Important 才是必须修复项。结论固定为：通过、有条件通过、不通过、输入不足。

## 审查意见处置门

| 处置 | 判定 | 后续 |
|---|---|---|
| 自动修复 | 明确违反已确认事实，证据充分，修复方案唯一或局部且不扩大范围 | 报告处置后直接修复并增量复审 |
| 需要用户确认 | 会改变行为、范围、契约、验收、工作流政策，或存在多个合理方案 | 标记 `needs_decision`，暂停修改并集中提问 |
| 仅记录建议 | Suggestion、风格偏好、非必要优化或当前范围外改进 | 不修改，不阻塞通过 |
| 驳回 | 与当前事实源不符、混淆状态层级、忽略优先级或缺少实际影响证据 | 不修改，记录反证 |

Suggestion 不得自动修复。工作流控制面的问题即使被 reviewer 标记为 Important，只要解决方式涉及政策取舍，也必须转为“需要用户确认”，不能借审查自动改写工作流。

审查失败按根因返回：实现问题回编码；需求或 UI 业务行为不明确回 `spec-analyzer`；范围遗漏回 `impact-analyzer`；布局、视觉或交互需要确认时回 `design-maker`；UI 技术落点或其他技术契约缺失回 `design-writer`。

## 审查状态

通过或有条件通过时写 `.claude/.review-status.json`，至少包含：

```json
{
  "status": "passed",
  "conclusion": "passed",
  "reviewer": "code-reviewer",
  "tier": "T1",
  "scope": "full",
  "accepted_risks": [],
  "uncovered_scope": [],
  "reviewed_files": [],
  "reviewed_file_hashes": {},
  "diff_fingerprint": "",
  "reviewed_at": ""
}
```

`status` 表示凭据是否可用于门禁，`conclusion` 使用 `passed / conditional / failed`。有条件通过必须填写 `accepted_risks`；部分审查必须填写 `uncovered_scope`，不得视为最终通过或提交凭据。`reviewer` 固定为 `code-reviewer`，不记录 Agent ID。文件哈希和 diff 指纹用于提交前确认代码未变。不在审查阶段生成 commit message。

## 报告规则

报告只保留结论、问题、覆盖范围、风险和回退路由；无问题时不生成空表。审查过程、Agent 名称/ID、查询流水不归档。

T2/T3 或用户要求归档时使用固定模板：

```markdown
# 代码审查报告

## 结论

通过 / 有条件通过 / 不通过 / 输入不足

## 问题

| 级别 | 文件 | 问题 | 建议 |
|---|---|---|---|

## 覆盖范围

| 项 | 内容 |
|---|---|
| 审查范围 | <完整 / 部分，说明未覆盖范围> |
| 需求依据 | <需求或设计来源> |
| 验证依据 | <局部检查或测试结果> |

## 风险与回退

| 项 | 说明 |
|---|---|
| 残余风险 | <短结论或 —> |
| 回退路由 | <编码 / 需求 / 影响面 / UI / 详设 / —> |
```

无问题时省略“问题”表，写一句“未发现阻塞问题”。T0/T1 无阻塞时可只写状态和一句结论。

存在候选问题时，在修复前先报告处置结果：

| 问题 | reviewer 级别 | 处置 | 依据 | 下一步 |
|---|---|---|---|---|

没有 `needs_decision` 时可继续自动修复已确认缺陷；存在 `needs_decision` 时必须等待用户确认。被驳回和仅记录建议的项目不得进入 `bug-fixer` 或 `dev-builder`。

## Qt 与注释检查

- 静态 Qt Widgets 控件是否优先使用已有 `.ui`，动态控件是否有真实必要性并正确处理所有权和线程。
- 新函数/类型 Doxygen 是否简洁；是否出现包含变量、函数调用和需求历史的长篇改动说明注释。

## 完成前自检

在写入审查通过凭据或输出审查报告前执行。未通过项先补充审查输入或退回对应阶段，不得用主 Agent 自审冒充独立审查。

- 是否确认使用独立 `code-reviewer`，没有主 Agent 自审冒充通过？
- 审查范围是否覆盖准备交付或提交的全部代码差异？
- 输入是否包含需求、设计、UI、验证和项目规范中的必要事实？
- 问题是否按 Critical、Important、Suggestion 排序并给出回退路由？
- 是否对 reviewer 候选问题逐项验真，没有把严重级别标签直接当作修改依据？
- Suggestion、误报和需要用户决策的问题是否没有被自动修改？
- 工作流控制面是否按当前工作流事实源审查，而非套用产品代码规则？
- 审查状态是否包含 reviewer、范围、文件哈希、diff 指纹和时间？
- 有条件通过是否记录接受风险与理由，部分审查是否记录未覆盖范围且未作为最终凭据？
- 是否没有生成 commit message 或记录 Agent ID/查询流水？
