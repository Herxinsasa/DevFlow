# Code Review - 独立代码审查

## 铁律

所有代码交付都需要独立审查。审查者不继承编码判断，不直接修改代码。不可用时不得写通过状态：T0/T1 可继续本地验证但不能提交，T2/T3 停止交付并通知用户。

## 审查深度

- T0：快速核对 diff、需求/验收和项目规范；干净时只记录状态与一句结论。
- T1：核对需求一致性、修改范围、局部回归和验证充分性；干净时不强制独立报告。
- T2/T3：完整检查契约、数据、UI、运行时、安全、性能和回归，归档 `docs/07-审查/<迭代ID>-代码审查.md`。

关联任务完成后统一审查，避免逐任务重复；早期集成、高风险接口或分批交付可中途审查。用户自测期间的 Bug 修复不逐次触发审查，用户明确要求或准备提交时统一审查当前最终差异。审查问题修复后只增量复审相关变化，最终凭据必须覆盖全部提交代码。

## 输入

- 实际 Git diff、变更文件和初始工作区快照。
- 关联需求与验收标准。
- T2/T3 详细设计及按需 UI 设计；T0/T1 简要影响和最小约束。
- 项目规范、局部验证结果和已知限制。

不依赖 Agent 执行流水。

## 结论

问题按 Critical、Important、Suggestion 排序。Critical/Important 必须修复。结论固定为：通过、有条件通过、不通过、输入不足。

审查失败按根因返回：实现问题回编码；需求歧义回需求；范围遗漏回影响面；UI 方案缺失回 `design-maker`；技术契约缺失回 `design-writer`。

## 审查状态

通过或有条件通过时写 `.claude/.review-status.json`，至少包含：

```json
{
  "status": "passed",
  "reviewer": "code-reviewer",
  "tier": "T1",
  "scope": "full",
  "reviewed_files": [],
  "reviewed_file_hashes": {},
  "diff_fingerprint": "",
  "reviewed_at": ""
}
```

`reviewer` 固定为 `code-reviewer`，不记录 Agent ID。文件哈希和 diff 指纹用于提交前确认代码未变。部分审查必须标明未覆盖范围，不得视为最终通过。不在审查阶段生成 commit message。

## 报告规则

报告只保留结论、问题、覆盖范围、风险和回退路由；无问题时不生成空表。审查过程、Agent 名称/ID、查询流水不归档。

## Qt 与注释检查

- 静态 Qt Widgets 控件是否优先使用已有 `.ui`，动态控件是否有真实必要性并正确处理所有权和线程。
- 新函数/类型 Doxygen 是否简洁；是否出现包含变量、函数调用和需求历史的长篇改动说明注释。
