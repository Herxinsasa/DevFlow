# Design Writer - 详细设计

## 定位

回答“如何实现”。只服务 T2/T3，或用户明确要求的 T1 例外。需求规格是业务事实源，影响面是范围事实源，`design-maker` 输出是已确认的 UI 事实源；本 Skill 不重复业务或视觉内容，不生成开发任务。

## 进入条件

- 需求规格已确认。
- 用户明确要求详设的 T1 已完成简要影响，或 T2/T3 影响面分析结论为“已闭合/受限闭合”且确认状态为“已确认”。
- 活动阻塞为零。
- 触发 UI 原型时，其输出已确认。

条件不满足时返回事实缺失的阶段，不用详细设计补写尚未确认的需求或范围。

## 工作原则

1. **结论有证据。** 关键设计来自用户确认、项目文档、影响面、图谱或源码；低置信度推断只能进入当前未决问题。
2. **契约可执行。** 接口、字段、默认值、错误、兼容和运行时约束必须具体，不能用“参考现有方式”等表述替代设计。
3. **最小充分。** 只设计本次编码需要遵守的事实、决策和边界，无关维度省略。
4. **技术栈中立。** UI、数据、通信和运行时设计遵循项目技术栈与项目约束，不在 Skill 内预设框架规则。
5. **一份设计闭合实现。** 非分离开发的跨层设计在同一文档中闭合；分离开发只在用户确认后建立独立接口契约。
6. **确认后计划。** 详细设计生成或实质修订后必须暂停；用户明确确认前不得进入 `dev-planner`。

## 输入与读取顺序

按以下顺序读取本次设计所需事实：

1. 用户当前确认。
2. 项目根说明、架构总览和相关模块设计。
3. 已确认需求规格、影响面和 UI 原型/界面稿。
4. 相关接口、数据、配置、业务文档和项目约束。
5. 图谱和源码，用于验证现有实现事实。

项目文档与源码冲突时展示冲突并等待用户处理。缺少模块框架时先确认名称、职责和层级，不根据代码自行建立长期架构事实。

## 模板文件

| 模板 | 用途 | 使用条件 |
|---|---|---|
| `references/需求设计_模板.md` | 当前迭代的需求设计 | 每次进入详细设计时生成或更新 |
| `references/模块设计_模板.md` | 模块长期事实 | 稳定职责、接口、数据或运行约束变化时回写 |
| `references/软件架构_模板.md` | 架构总览参考 | 架构边界、部署、协议、技术选型或数据归属变化时回写 |

需求设计服务当前编码；模块设计和架构总览服务长期知识。一次性需求细节不得回写为长期事实。

## 工作流程

### Step 1：确认设计范围

从已确认需求和影响面提取本次设计内容、不变边界、关键代码位置和验证重点。没有需求或范围依据的内容不进入设计。

### Step 2：复核当前技术事实

使用项目文档、图谱和源码确认相关接口、数据、配置、依赖和运行时行为。图谱与源码冲突时以源码为当前实现事实；无法解释的冲突列为活动阻塞。

### Step 3：形成可执行设计

按需求项写明：

- 接口、数据、配置、错误和兼容契约。
- 关键技术决策、选择理由和不采用方案的必要说明。
- 实际涉及的线程、异步、并发、缓存、生命周期、性能、升级和回退约束。
- UI 的技术落点、组件/对象边界、事件、状态、数据映射和生命周期；布局与视觉引用已确认原型。
- 关键实现位置、允许范围、不变边界和验证重点。

内部辅助函数不必穷举，业务验收引用需求规格，不复制全文，不包含 `TASK-xxx`、Agent 信息或逐步编码过程。

### Step 4：处理跨端契约

前后端或客户端/服务端由不同维护方并行开发且存在通信契约时，先向用户确认是否建立独立接口契约：

- 非分离开发：契约保留在需求设计正文。
- 分离开发且用户确认：生成 `docs/04-设计/接口契约/<迭代ID>-接口契约.md`。
- 独立契约只写共享边界；维护方确认接口、字段、错误和兼容，消费方确认可消费性、默认值和异常处理。

双方确认前不得进入计划。已确认契约发生实质变化时，使依赖它的设计、任务、审查和验证凭据失效，并回到受影响阶段。

### Step 5：记录未决问题与待回写项

影响编码的低置信度内容集中写入当前未决问题，不得进入技术契约或实现边界。只记录实现完成后需要回写的稳定模块或架构事实，不在设计阶段提前改写长期文档。

### Step 6：输出详细设计

使用 `references/需求设计_模板.md` 写入：

```text
docs/04-设计/需求设计/<迭代ID>-需求设计.md
```

首次生成或实质修订后将文档状态设为“待确认”。编码相关未决项可以保留在文档中供用户处理，但不得流入开发计划。

### Step 7：等待用户确认

向用户提供文档路径和简短确认摘要，只列设计范围、关键决策、契约变化、运行时风险、回退方案和当前未决问题，并明确标记“需要确认”。同步将当前流程置为 `waiting_confirmation`，然后停止，不自动调用 `dev-planner`。

用户明确确认后，将文档状态更新为“已确认”；只有编码相关未决项归零时才能进入计划。用户提出修改时更新原文档并再次保持“待确认”。

## 长期文档回写

详设只记录待回写事项。编码和验证完成后，根据最终实现更新：

- 模块设计：稳定职责、外部接口、核心数据、状态流程、依赖、配置和运行约束。
- 架构总览：真实架构边界、部署、协议、技术选型或数据归属变化。

不把一次性需求细节或 AI 推理写入长期文档。

## 完成前自检

在提示用户确认前执行：

- 需求、影响面和按需 UI 原型是否已经确认？
- 设计范围和关键结论是否有可追溯证据？
- 接口、数据、配置、错误、兼容和运行时约束是否能直接指导编码？
- 是否遵循项目技术栈与项目约束，没有硬编码框架规则？
- 非分离开发的跨层实现是否在同一份设计中闭合？
- 低置信度内容是否只在当前未决问题中，没有流入计划？
- 是否没有任务拆分、重复验收、视觉布局和过程说明？
- 文档是否处于“待确认”，且流程已暂停而不是自动进入计划？
