# Design Writer - 详细设计

## 定位

回答“如何实现”。只服务 T2/T3，或用户明确要求的 T1 例外。需求规格是业务事实源，影响面是范围事实源，`design-maker` 输出是已确认的 UI 事实源；本 Skill 不重复业务或视觉内容，不生成开发任务。

## 进入条件

- 需求规格已确认。
- 用户明确要求详设的 T1 已完成简要影响，或 T2/T3 影响面分析结论为“已闭合/受限闭合”且确认状态为“已确认”。
- 活动阻塞为零。
- 触发 UI 原型时，其输出已确认。

条件不满足时返回事实缺失的阶段，不用详细设计补写尚未确认的需求或范围。

## 工作原则

1. **结论有证据。** 关键设计来自用户确认、项目文档、影响面、图谱或源码；低置信度推断只能进入当前未决问题。
2. **设计可执行。** 按公开类型、核心数据、适配器、管理或服务层、对外接口等真实设计对象和依赖顺序组织；需求 ID 只作追溯，不作为主体章节。
3. **最小充分。** 只设计本次编码需要遵守的事实、决策和边界，无关维度省略。
4. **技术栈中立。** UI、数据、通信和运行时设计遵循项目技术栈与项目约束，不在 Skill 内预设框架规则。
5. **契约单一来源。** 同一维护边界内的调用在需求设计中闭合；独立通信边界的共享接口、字段、错误和兼容规则写入接口契约，需求设计只引用并说明内部实现与映射。
6. **确认后计划。** 详细设计生成或实质修订后必须暂停；用户明确确认前不得进入 `dev-planner`。

## 输入与读取顺序

按以下顺序读取本次设计所需事实：

1. 用户当前确认。
2. 项目根说明、架构总览和相关模块设计。
3. 已确认需求规格、影响面和 UI 原型/界面稿。
4. 相关接口、数据、配置、业务文档和项目约束。
5. 图谱和源码，用于验证现有实现事实。

项目文档与源码冲突时展示冲突并等待用户处理。缺少模块框架时先确认名称、职责和层级，不根据代码自行建立长期架构事实。

## 文档准备

生成或实质修改需求设计、接口契约、模块设计或架构总览前，读取适用项目文档规范；项目未覆盖的部分读取 `.claude/constraints/document-req.md`。恢复阶段已读取的约束可复用；新会话、新执行 Agent 或约束变化后重新读取。

## 模板文件

| 模板 | 用途 | 使用条件 |
|---|---|---|
| `references/需求设计_模板.md` | 当前迭代的需求设计 | 每次进入详细设计时生成或更新 |
| `references/接口契约_模板.md` | 跨端共享通信边界 | 独立通信边界存在新增或变化时自动生成或更新 |
| `references/模块设计_模板.md` | 模块长期事实 | 稳定职责、接口、数据或运行约束变化时回写 |
| `references/软件架构_模板.md` | 架构总览参考 | 架构边界、部署、协议、技术选型或数据归属变化时回写 |

需求设计服务当前编码；模块设计和架构总览服务长期知识。一次性需求细节不得回写为长期事实。

## 工作流程

### Step 1：确认设计范围

从已确认需求和影响面提取本次设计内容、不变边界、关键代码位置和验证重点。没有需求或范围依据的内容不进入设计。

### Step 2：复核当前技术事实

使用项目文档、图谱和源码确认相关接口、数据、配置、依赖和运行时行为。图谱与源码冲突时以源码为当前实现事实；无法解释的冲突列为活动阻塞。

### Step 3：形成可执行设计

先列出本次真实设计对象，再按依赖顺序组织章节：公开类型与配置、核心数据与状态、适配器或基础设施、管理器或服务层、对外接口或 UI。不存在的层跳过，同一层按调用或数据依赖排序。章节标题使用真实类型、组件或职责名称；所属层级、关联需求、代码位置和参考实现写在正文，不写入标题括号。

每个设计对象使用模板规定的固定信息槽，说明作用与边界、现有基础与改动位置、类型/接口/数据定义、协作行为、实际涉及的错误/生命周期/兼容约束、实现边界和验证重点。只有存在真实方案取舍时才记录技术决策和理由，不为填满模板制造内容。

内部辅助函数不必穷举，业务验收引用需求规格，不复制全文，不包含 `TASK-xxx`、Agent 信息或逐步编码过程。

### Step 4：处理跨端契约

根据影响面和源码判断是否存在跨进程、跨工程、独立发布或不同维护方消费的通信边界。只要本次新增或修改接口、通知、共享消息、字段、枚举、错误码或兼容规则，就使用 `references/接口契约_模板.md` 自动生成或更新：

```text
docs/04-设计/接口契约/<迭代ID>-接口契约.md
```

不等待用户主动要求或先确认是否生成。契约按业务模块、错误码、枚举定义、接口列表、通知列表和兼容记录组织；每个接口和通知必须有规范字段表及调用形态，REST 与 RPC 使用各自调用定义，示例不能替代入参、出参和约束。

同一维护边界内的内部调用写入需求设计，不单独建契约。独立契约生成或实质修订后置为“待确认”；维护方确认定义，消费方确认可消费性、默认值和异常处理。确认前不得进入计划。已确认契约发生实质变化时，使依赖它的设计、任务、审查和验证凭据失效，并回到受影响阶段。

### Step 5：记录未决问题与待回写项

影响编码的低置信度内容集中写入当前未决问题，不得进入技术契约或实现边界。只记录实现完成后需要回写的稳定模块或架构事实，不在设计阶段提前改写长期文档。

### Step 6：输出设计产物

使用 `references/需求设计_模板.md` 写入：

```text
docs/04-设计/需求设计/<迭代ID>-需求设计.md
```

首次生成或实质修订后将文档状态设为“待确认”。编码相关未决项可以保留在文档中供用户处理，但不得流入开发计划。

### Step 7：等待用户确认

向用户提供需求设计及按需接口契约的路径和简短确认摘要，只列设计范围、关键决策、契约变化、运行时风险、回退方案和当前未决问题，并明确标记“需要确认”。同步将当前流程置为 `waiting_confirmation`，然后停止，不自动调用 `dev-planner`。

用户明确确认后，将文档状态更新为“已确认”；只有编码相关未决项归零时才能进入计划。用户提出修改时更新原文档并再次保持“待确认”。

## 长期文档回写

详设只记录待回写事项。编码和验证完成后，根据最终实现更新：

- 模块设计：稳定职责、外部接口、核心数据、状态流程、依赖、配置和运行约束。
- 架构总览：真实架构边界、部署、协议、技术选型或数据归属变化。

不把一次性需求细节或 AI 推理写入长期文档。

## 完成前自检

在提示用户确认前执行：

- 需求、影响面和按需 UI 原型是否已经确认？
- 设计范围和关键结论是否有可追溯证据？
- 是否按真实设计对象和依赖顺序组织，需求 ID 只作追溯，没有按 REQ 机械分块？
- 每个设计对象的类型、接口、数据、协作和实际运行约束是否能直接指导编码？
- 是否遵循项目技术栈与项目约束，没有硬编码框架规则？
- 独立通信边界发生契约变化时，是否自动生成或更新接口契约并完整描述入参、出参、错误、枚举和通知？
- 同一维护边界内的实现是否在需求设计中闭合，没有重复创建契约？
- 低置信度内容是否只在当前未决问题中，没有流入计划？
- 是否没有任务拆分、重复验收、视觉布局和过程说明？
- 文档是否处于“待确认”，且流程已暂停而不是自动进入计划？
