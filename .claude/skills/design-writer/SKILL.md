# Design Writer - 详细设计

## 定位

回答“如何实现”。只服务 T2/T3，或用户明确要求的 T1 例外。T1 若客观需要正式详设，原则上应升级为 T2。

需求规格是业务事实源，影响面是范围事实源，`design-maker` 输出是 UI 原型或界面稿源。本文不重复这些内容，也不生成开发任务。

## 工作原则

1. **结论有证据**：关键设计结论必须来自用户确认、项目文档、影响面证据、图谱或源码复核；无法证明的推断只能进入当前未决问题。
2. **契约可执行**：接口签名、字段类型、默认值、错误处理、兼容策略和 UI 行为必须具体，禁止使用“参考现有方式”“按需处理”等无法直接指导编码的表述。
3. **低置信度禁入计划**：影响实现方向、范围、契约或验收的低置信度内容未确认前，不得写成实现边界或流入 `dev-planner`。
4. **最小充分设计**：只设计本次编码必须遵守的事实、决策和边界；无关维度省略，不为模板完整而扩写。
5. **一份设计闭合实现**：非分离开发的客户端/前端与服务端/后端技术设计在同一文档中闭合，不能让跨层契约分散在互不确认的文档里。
6. **运行时风险前置**：实际涉及线程、并发、缓存、资源生命周期、异步取消、性能、升级或回退时，在设计阶段明确约束，不留给编码阶段临时决定。

## 进入条件

- 需求规格已确认。
- 完整影响面状态为“已闭合”或经用户确认的“受限闭合”。
- 活动阻塞为零。
- 触发 UI 原型时，其输出已确认。

## 设计前读取顺序

1. 用户当前确认。
2. 根目录项目说明、`docs/01-总览/架构总览.md` 和既有模块设计。
3. 相关需求、接口、业务和 UI 文档。
4. 已确认需求规格、影响面和 UI 原型/界面稿。
5. 图谱和源码，用于验证现有实现事实。

项目文档与源码冲突时展示冲突并询问用户。文档缺失时不得根据代码自行建立模块框架；模块名称、职责和层级先由用户确认。AI 推测只能放入当前阻塞问题。

## 模板文件

| 模板 | 用途 | 规则 |
|---|---|---|
| `references/需求设计_模板.md` | 单次需求输入的需求设计文档 | 每次进入详细设计时生成或更新 |
| `references/模块设计_模板.md` | 模块长期事实 | 仅稳定职责、接口、核心数据或运行约束变化时回写 |
| `references/软件架构_模板.md` | 架构总览参考 | 仅架构边界、部署、协议、技术选型或数据归属变化时回写 |

需求设计服务当前迭代编码；模块设计和架构总览服务长期知识沉淀。不要把一次性需求细节回写到长期文档。

## 必须设计的内容

- 设计范围与不变边界。
- 接口、数据、配置、错误和兼容契约。
- 关键技术决策及选择理由。
- 涉及时的线程、并发、缓存、生命周期、性能、升级和回退约束。
- UI 的技术落点：`.ui`/类/组件、信号、状态、数据映射和生命周期；不重复视觉布局。
- 关键代码位置和实现边界。
- 验证重点、未决问题和实现后待回写事项。

## 分离开发接口契约

需求涉及前后端或客户端/服务端由不同维护方并行开发，且存在跨端通信契约时，先向用户确认是否产出独立接口契约。

- 非分离开发：契约写在需求设计正文，不单独建文档。
- 分离开发且用户确认：生成 `docs/04-设计/接口契约/<迭代ID>-接口契约.md`。
- 接口契约只写边界，不写内部实现。明确契约维护方和消费方：维护方确认接口、字段、错误与兼容规则，消费方确认可消费性、默认值和异常处理；双方确认前不得进入 `dev-planner`。
- 已确认契约发生实质变化时，标记依赖该契约的设计、任务、审查和验证凭据失效，回到受影响阶段重新确认。

内部辅助函数不必穷举，验收标准引用需求规格，不复制全文。不得包含 `TASK-xxx`、实现分解建议、Agent 信息或逐步编码过程。

## 工作流程

1. 读取已确认需求、影响面、UI 原型/界面稿、架构总览、模块设计和项目约束。
2. 使用图谱和源码复核关键事实；图谱与源码冲突时以源码为准，无法解释则列为阻塞。
3. 按需求项写设计范围、契约、技术决策、运行时约束和实现边界；每个关键决策记录证据或约束来源。
4. 涉及 UI 时只写技术落点和数据/状态/生命周期，不重复原型和视觉布局。
5. 涉及跨端、协议、公共类型或数据持久化时，明确兼容、错误处理、默认值和回退策略。
6. 记录验证重点、未决问题和长期文档待回写事项。
7. 输出后提示用户确认；编码相关 TBD 未清零不得进入计划。

## 输出

使用 `references/需求设计_模板.md`，写入：

```text
docs/04-设计/需求设计/<迭代ID>-需求设计.md
```

前后端由不同维护方并行开发且需要共同协议时，可经用户确认另建轻量接口契约；否则契约保留在同一详设中。

设计完成后提示“需要确认”。影响编码的 TBD 必须归零。

## 长期文档回写

详设只记录“待回写”事项。编码和验证后根据最终实现更新：

- 模块设计：稳定职责、外部接口、核心数据、状态流程、依赖、配置和运行约束。
- 架构总览：真实架构边界、部署、协议、技术选型或数据归属变化。

不把一次性需求细节或 AI 推理写入长期文档。修订记录仅记录确认后的重大技术变化。

## 完成前自检

在提示用户确认详细设计前执行。未通过项先修正；编码相关未决项未清零时，不得进入开发计划。

- 是否基于项目设计文档而非自行推理模块框架？
- 是否只写稳定技术契约和必要决策，且关键结论有可追溯证据？
- 是否完成图谱/源码复核，并处理冲突？
- 接口、数据、配置、错误、兼容和运行时约束是否具体到可以直接指导编码？
- 是否没有把低置信度推断写成实现事实或带入开发计划？
- 非分离开发的跨层实现是否在同一份设计中闭合？
- 是否删除任务拆分、重复验收和过程说明？
- UI 原型与 UI 技术实现职责是否分开？
- 所有编码相关未决项是否已清零？
