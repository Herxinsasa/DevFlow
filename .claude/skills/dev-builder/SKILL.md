# Dev Builder - 编码调度

## 执行策略

| 场景 | 执行者 |
|---|---|
| T0、简单 T1 | 主 Agent 可直接编码 |
| T1 多个独立边界或适合并行 | 按需使用 implementer |
| T2/T3 | 必须调用独立 implementer |

同模块、共享行为和连续任务可复用一个 implementer；机械重复接入整体派发一次，不按任务行强制新建。implementer 不可用时，T0/T1 可由主 Agent继续；T2/T3 必须标记阻塞，只有用户明确确认降级后才可由主 Agent实施并加强独立审查。

## 执行前检查

- 检查计划、需求、影响面、详细设计和 UI 原型/界面稿是否满足当前任务需要；触发 `ui-designer` 的任务必须已有用户确认产物。
- 复制或修改 Agent 文件后，应提示重启 Claude Code，使 `.claude/agents/` 生效。
- 缺少需求、接口、数据、UI 或运行时契约时返回前置阶段，不把猜测写成编码输入。

## 输入

- 当前任务及关联 `REQ-xxx`。
- T2/T3 的详细设计相关章节；T0/T1 的简要影响和最小实现约束。
- 按需 UI 原型/界面稿；未触发独立 UI 设计时读取目标页面和同类界面作为实现基线。
- 项目约束、同目录代表性代码和允许范围。

只提供当前行为需要的上下文，不重新收集整套文档。

编码输入至少确认以下信息，作为内部执行清单，不写入开发计划：

| 项 | 要求 |
|---|---|
| 当前任务目标 | 明确本次要交付的行为 |
| 来源需求 | 对应 `REQ-xxx` 或用户确认 |
| 允许修改范围 | 可修改的模块、文件或对象 |
| 禁止修改范围 | 不得触碰的业务、接口或用户已有改动 |
| 目标文件或对象 | 主要落点、参考实现和相邻代码 |
| 验收标准 | 可验证结果和边界场景 |
| 契约约束 | 接口、数据、UI、配置、错误和兼容要求 |
| 运行约束 | 线程、生命周期、缓存、资源、性能等实际涉及项 |
| 编码约束 | 命名、日志、注释、编码、BOM、EOL 和项目风格 |

## 编码前规范加载

按优先级读取并注入编码输入：

1. 用户本次明确要求。
2. 项目根 `CLAUDE.md` 和项目文档中的开发约束。
3. 仓库或模块编码、接口、错误码、测试和日志规范。
4. `.claude/constraints/coding-req.md`、`.claude/constraints/log-req.md` 默认基线。
5. 目标文件同目录或同模块中，足以确认项目写法的最少量代表性代码。

编码前确认字符集、BOM、行尾、命名、缩进、注释、日志和代码组织顺序。项目约定优先于 DevFlow 默认基线；冲突或缺失会影响编码时，先提示用户或返回阻塞。

约束注入属于内部上下文组装，正常执行时不逐条向用户复述。只有约束冲突、关键约束缺失，或某项约束会实质改变实现方向和范围时，才在执行前说明并请求确认。

## 执行步骤

1. 核对基线和工作区，保留用户原有修改；只选择待执行、依赖已满足且无活动阻塞或待确认项的 `TASK-xxx`。没有可执行任务时，区分完成、依赖阻塞、等待用户确认，或仅剩 `VERIFY-xxx`。
2. T2/T3 先确认 `implementer` 可调用；不可用时记录 `BLOCKED_AGENT_UNAVAILABLE`，不写入执行中、不直接编码。确认可以开始后，将任务更新为执行中并同步 `progress.json`。
3. 按“输入”和“编码前规范加载”组装任务包；T2/T3 补充详细设计、运行时和接口/数据契约，UI 任务补充已确认 UI 事实和现有界面基线，跳过详设的任务补充影响面实现要点。缺少关键契约或应确认的 UI 设计时回前置阶段。
4. 按执行策略实施：T0、简单 T1 可由主 Agent 编码；T1 按需调用 `implementer`；T2/T3 必须调用 `implementer` 并传入任务包，主 Agent 不得代替编码。派发只允许当前范围和验收标准，禁止计划外修改。
5. 按下方返回状态做任务级对齐和路由；可修复偏差只针对同一任务重新派发，`NEEDS_CONTEXT` 或 `BLOCKED` 不得标记完成。
6. 写回状态、主要修改文件、短变更摘要、局部检查、风险或阻塞原因，随后选择下一任务；只剩验证项时进入 `code-review` 和 `code-tester`。

开发计划只更新当前状态和必要阻塞，不追加执行时间、Agent 名称、Agent ID 或过程日志。

## 执行结果协议

独立 implementer 必须返回以下状态之一；T2/T3 只接受实际调用的 implementer 返回结果，主 Agent 的直接编码不能替代该结果。T0/T1 主 Agent 直接编码时按同一语义判断结果：

| 状态 | 处理 |
|---|---|
| `DONE` | 完成任务级对齐检查，写回已完成和当前结果 |
| `DONE_WITH_CONCERNS` | 检查关注项；不影响交付时记录风险并完成，影响验收或契约时转为阻塞 |
| `NEEDS_CONTEXT` | 不继续编码，写明缺失事实并回需求、影响面、UI 或详细设计 |
| `BLOCKED` | 写明环境、依赖、权限或外部阻塞，不把任务标记完成 |

返回内容至少包括任务 ID、修改摘要、主要文件、局部验证、范围检查和关注事项。修改非 UTF-8 文件、含中文文件或发生编码/BOM 变化时，局部验证必须包含实际编码检查结果；无法严格解码或新增 U+FFFD 时不得标记完成。低置信度内容、活动问题和阻塞项不得转换成实现指令。

## 输出

- 当前任务状态和变更摘要。
- 主要修改文件和写回开发计划的当前结果。
- 局部检查结果或无法执行原因。
- 下一任务、活动阻塞或进入独立审查的建议。

关联任务完成后统一进入独立 `code-review`，不要求每个小任务单独终审。

## 完成前自检

在标记任务完成、阻塞或交给下一阶段前执行。未通过项先修正；缺少需求、接口、数据或 UI 契约时回到对应前置阶段。

- 是否只读取当前任务需要的最小上下文？
- 是否保留并避开用户既有无关修改？
- T2/T3 是否已实际调用 implementer；未调用时是否保持阻塞或取得用户明确降级确认？
- 执行者选择是否符合任务等级和复杂度，而非机械每任务新建 Agent？
- 是否缺少需求、接口、数据或 UI 契约时停止并回前置阶段？
- 编码与日志规范是否已注入，项目代表性代码是否已读取？
- 命中编码风险条件时，是否有实际检查结果而非仅凭执行者声明通过？
- 局部检查是否执行或说明无法执行原因？
- implementer 返回状态是否按统一协议处理，没有把 `NEEDS_CONTEXT` 或 `BLOCKED` 标记为完成？
- 开发计划是否更新当前状态、结果和必要证据，同时没有过程流水？
