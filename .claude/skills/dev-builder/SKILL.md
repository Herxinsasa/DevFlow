# Dev Builder - 编码调度

## 执行策略

| 场景 | 执行者 |
|---|---|
| T0、简单 T1 | 主 Agent 可直接编码 |
| T1 多个独立边界或适合并行 | 按需使用 implementer |
| T2/T3 | 必须调用独立 implementer |

同模块、共享行为和连续任务可复用一个 implementer；机械重复接入整体派发一次，不按任务行强制新建。implementer 不可用时，T0/T1 可由主 Agent继续；T2/T3 必须标记阻塞，只有用户明确确认降级后才可由主 Agent实施并加强独立审查。

## 执行前检查

- 检查计划、需求、影响面、详细设计和 UI 原型/界面稿是否满足当前任务需要；触发 `ui-designer` 的任务必须已有用户确认产物。
- 复制或修改 Agent 文件后，应提示重启 Claude Code，使 `.claude/agents/` 生效。
- 缺少需求、接口、数据、UI 或运行时契约时返回前置阶段，不把猜测写成编码输入。

## 输入

- 当前任务及关联 `REQ-xxx`。
- T2/T3 的详细设计相关章节；T0/T1 的简要影响和最小实现约束。
- 按需 UI 原型/界面稿；未触发独立 UI 设计时读取目标页面和同类界面作为实现基线。
- 项目约束、同目录代表性代码和允许范围。

只提供当前行为需要的上下文，不重新收集整套文档。每个 `TASK` 开始前重新读取相关代码和约束；同一 implementer 连续执行也不能沿用上一任务未经核对的风格记忆。

编码输入至少确认以下信息，作为内部执行清单，不写入开发计划：

| 项 | 要求 |
|---|---|
| 当前任务目标 | 明确本次要交付的行为 |
| 来源需求 | 对应 `REQ-xxx` 或用户确认 |
| 允许修改范围 | 可修改的模块、文件或对象 |
| 禁止修改范围 | 不得触碰的业务、接口或用户已有改动 |
| 目标文件或对象 | 主要落点、同层同类参考符号及真实调用路径；同目录代码只补格式依据 |
| 验收标准 | 可验证结果和边界场景 |
| 契约约束 | 接口、数据、UI、配置、错误和兼容要求 |
| 运行约束 | 线程、生命周期、缓存、资源、性能等实际涉及项 |
| 编码约束 | 命名、日志、注释、目标编码、BOM、EOL、项目格式器检查命令和风格依据 |
| 既有实现机制 | 当前场景适用的注册、转换、工厂、适配机制及入参/出参调试开关、日志和错误路径 |
| 权威类型来源 | 公共接口、算法或跨模块数据类型的定义文件、符号及版本 |
| 测试执行方式 | 已确认用例及是否选用 TDD；未选用时沿用项目常规测试方式 |

## 编码前规范加载

从下列来源读取并注入编码输入；用户注入约束与既有规则有冲突时按总控确认和优先级规则处理：

1. 用户本次明确要求。
2. 项目根 `CLAUDE.md` 和项目文档中的开发约束。
3. 仓库或模块编码、接口、错误码、测试和日志规范。
4. 读取总控扫描发现且适用于本任务的用户新增约束，并按总控解析 `coding`、`logging` 领域约束；无配置时读取 `.claude/constraints/coding-req.md`、`.claude/constraints/log-req.md`，`extend/replace` 按解析结果执行。冲突先说明并取得用户确认，确认后以注入约束为主。
5. 目标文件同层同类实现、权威接口定义，以及足以确认格式的最少量相邻代码。

编码前确认字符集、BOM、行尾、命名、缩进、注释、日志、代码组织顺序和当前场景适用的既有实现机制。沿真实调用路径核对同层同类实现，查明注册、转换、工厂等扩展入口是否适用，并读取权威头文件或契约；算法接入还要确认相邻算法的入参/出参调试开关和错误处理。若现有 `TYPE_CONVERT_EX_REGISTER` / `CONVERT` 路径可承载，不派发等价 `toXxx` 辅助转换。用户注入约束和项目约定优先于 DevFlow 默认基线，实质冲突先按总控提示用户确认；关键参考实现、权威类型来源或约束缺失会影响实现时，先提示用户或返回阻塞。

派发前将关键参考路径与符号、机制适用结论、权威类型、文件格式画像和允许/禁止范围组成简短实现依据，注入当前任务包；只把这些关键定位与检查结论写入该 `TASK` 的恢复信息，不复制代码或调查流水。T0 无计划时写入当前结果。下一任务重新取证并更新其自身恢复信息。

约束注入属于内部上下文组装，正常执行时不逐条向用户复述。只有约束冲突、关键约束缺失，或某项约束会实质改变实现方向和范围时，才在执行前说明并请求确认。

## 执行步骤

1. 核对基线和工作区，保留用户原有修改；只选择待执行、依赖已满足且无活动阻塞或待确认项的 `TASK-xxx`。没有可执行任务时，区分完成、依赖阻塞、等待用户确认，或仅剩 `VERIFY-xxx`。
2. T2/T3 先确认 `implementer` 可调用；不可用时记录 `BLOCKED_AGENT_UNAVAILABLE`，不写入执行中、不直接编码。
3. 在任务开始前按“输入”和“编码前规范加载”重新组装实现依据；T2/T3 补充详细设计、运行时和接口/数据契约，UI 任务补充已确认 UI 事实和现有界面基线，跳过详设的任务补充影响面实现要点。缺少影响编码方向的参考机制、权威类型、关键契约或应确认的 UI 设计时回前置阶段或保持阻塞，不派发。依据齐备后才将任务更新为执行中并同步 `progress.json`。
   已选择 TDD 时，将当前可观察用例和逐个行为的红、绿、重构要求放入任务包；不要求先批量写完所有测试。未选择 TDD 时，不因存在 `test-designer` 用例而改写任务执行方式。
4. 按执行策略实施：T0、简单 T1 可由主 Agent 编码；T1 按需调用 `implementer`；T2/T3 必须调用 `implementer` 并传入任务包，主 Agent 不得代替编码。派发只允许当前范围和验收标准，禁止计划外修改。
5. 核对 implementer 的实际命令与输出；主 Agent 自行编码、证据缺失或代码检查后变化时，对本任务修改的每个文本源文件按目标编码、BOM 和行尾调用 `.claude/scripts/check-source-file.py`，原文件已有 U+FFFD 时传入编辑前快照。再运行项目已有格式器的检查模式或对应静态格式检查，只针对本次文件，不因局部任务重排全仓库。工具失败、格式器不可用或项目约定不明时记录实际限制并处理，不能凭执行者一句“格式正确”标记通过。

   调用形式：`python .claude/scripts/check-source-file.py --root <项目根> --file <相对路径> --encoding <目标编码> --bom require|forbid --eol lf|crlf [--baseline <编辑前快照> --baseline-encoding <原编码>]`。文件与配置先由当前任务事实确定；脚本不猜编码或自动改写文件。
6. 按下方返回状态做任务级对齐和路由；可修复偏差只针对同一任务重新派发，`NEEDS_CONTEXT` 或 `BLOCKED` 不得标记完成。
7. 写回状态、主要修改文件、短变更摘要、局部检查、风险或阻塞原因，随后选择下一任务；只剩验证项时进入 `code-reviewer` 和 `code-tester`。

开发计划只更新当前状态和必要阻塞，不追加执行时间、Agent 名称、Agent ID 或过程日志。

## 执行结果协议

独立 implementer 必须返回以下状态之一；T2/T3 只接受实际调用的 implementer 返回结果，主 Agent 的直接编码不能替代该结果。T0/T1 主 Agent 直接编码时按同一语义判断结果：

| 状态 | 处理 |
|---|---|
| `DONE` | 完成任务级对齐检查，写回已完成和当前结果 |
| `DONE_WITH_CONCERNS` | 检查关注项；不影响交付时记录风险并完成，影响验收或契约时转为阻塞 |
| `NEEDS_CONTEXT` | 不继续编码，写明缺失事实并回需求、影响面、UI 或详细设计 |
| `BLOCKED` | 写明环境、依赖、权限或外部阻塞，不把任务标记完成 |

返回内容至少包括任务 ID、修改摘要、主要文件、局部验证、文件检查与格式器结果、范围检查和关注事项；选用 TDD 时，简记每个行为的预期失败、通过与重构后复测证据，不保留冗长终端流水。无法按目标编码严格解码、BOM/行尾不符或新增 U+FFFD 时不得标记完成。低置信度内容、活动问题和阻塞项不得转换成实现指令。

## 输出

- 当前任务状态和变更摘要。
- 主要修改文件和写回开发计划的当前结果。
- 局部检查结果或无法执行原因。
- 下一任务、活动阻塞或进入独立审查的建议。

关联任务完成后统一进入独立 `code-reviewer`，不要求每个小任务单独终审。

## 完成前自检

在标记任务完成、阻塞或交给下一阶段前执行。未通过项先修正；缺少需求、接口、数据或 UI 契约时回到对应前置阶段。

- 是否只读取当前任务需要的最小上下文？
- 是否保留并避开用户既有无关修改？
- T2/T3 是否已实际调用 implementer；未调用时是否保持阻塞或取得用户明确降级确认？
- 执行者选择是否符合任务等级和复杂度，而非机械每任务新建 Agent？
- 是否缺少需求、接口、数据或 UI 契约时停止并回前置阶段？
- 编码与日志规范是否已注入，同层同类实现、权威类型来源和适用的既有实现机制是否已确认？
- 当前 `TASK` 是否在派发前重新取证，并将关键路径/符号、机制、权威类型与文件格式结论写入恢复信息？
- 本任务修改的文本源文件是否实际通过编码/BOM/行尾/U+FFFD 检查和项目格式器检查，未扫描或重排无关文件？
- 局部检查是否执行或说明无法执行原因？
- implementer 返回状态是否按统一协议处理，没有把 `NEEDS_CONTEXT` 或 `BLOCKED` 标记为完成？
- 开发计划是否更新当前状态、结果和必要证据，同时没有过程流水？
