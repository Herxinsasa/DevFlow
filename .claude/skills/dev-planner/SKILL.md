# Dev Planner - 开发计划

## 定位

开发计划只回答“派发哪些任务、目前做到哪里、如何验证”。业务事实以需求规格为准，UI 原型/界面稿以 design-maker 输出为准，技术方案以详细设计为准。

T0 通常不归档计划；跨会话或确需恢复时可创建极简计划。T1/T2/T3 归档计划，生成后“建议查阅”，不作为新的审批门。

## 进入条件

- 需求已确认，活动阻塞为零。
- T0/T1 简要影响已完成并写回需求规格，或 T2/T3 独立影响面已确认。
- T2/T3 详细设计已确认；触发 UI 原型时其状态已确认。

任一条件不满足时只记录阻塞，不生成可执行任务，不以计划内容替代缺失决策。

## 输入

| 输入 | 用途 |
|---|---|
| `docs/02-需求/<迭代ID>-需求.md` | 已确认范围和验收标准 |
| 需求规格中的简要影响结论 | T0/T1 的影响对象、局部风险和最小实现约束 |
| `docs/02-需求/<迭代ID>-影响面.md` | T2/T3 的闭合链路、关键路径、聚合风险和实现边界 |
| `docs/04-设计/需求设计/<迭代ID>-需求设计.md` | 技术契约、实现边界和验证重点 |
| `docs/05-UI/原型/<迭代ID>/` | 涉及 UI 且已触发原型时的界面依据 |
| 代码基线 | 区分当前迭代和用户已有改动 |

没有 UI 原型必要性时不读取 UI 原型；跳过详细设计的需求项从影响面实现要点生成任务。

## 任务拆分

- 按可独立交付的行为拆分，不按文件、函数、类或工具数量拆分。
- 使用能够表达真实依赖和独立交付边界的最少任务，不预设任务数量或工时阈值。
- 多个工具接入同一事件处理逻辑通常合并为一个任务。
- 生产代码和自动化测试代码可作为 `TASK-xxx`；构建、审查、测试执行和用户验收属于 `VERIFY-xxx`。
- T2/T3 任务引用详细设计章节，不复制技术细节；T0/T1 只保留一句最小实现约束。

## 基线

创建计划时记录：

- 基线标识：Git commit、SVN revision，或无版本控制时的文件快照/哈希。
- 初始工作区状态。
- 初始修改文件。

基线变化不自动阻塞；只有目标代码事实或契约变化时才重新检查影响面。用户原有修改不得自动纳入或回退。

## 工作流程

1. 检查进入条件。任一前置文档未确认或活动阻塞未清零时，只记录阻塞，不生成可执行任务。
2. 根据 Git、SVN 或无版本控制模式记录基线标识、初始工作区状态和初始修改文件，用于区分本次迭代与用户已有改动。
3. 从需求、影响面、UI 原型/界面稿和详细设计中提取任务输入，只引用章节和最小约束，不复制技术细节。
4. 按可独立交付行为生成 `TASK-xxx`；同一事件处理、重复工具接入和连续同模块修改优先合并。
5. 将构建、测试、审查、用户验收和手动场景列入 `VERIFY-xxx`，不混入编码任务。
6. 分析依赖、冲突和阻塞。只有真实并行或冲突存在时才写说明。
7. 为任务和验证项预留当前结果字段，使中断恢复时能知道实际修改与验证到哪里；不记录时间线或 Agent 流水。
8. 输出前检查任务数量、粒度、依赖、验证覆盖和恢复状态。

## 输出

写入 `docs/08-计划/<迭代ID>-开发计划.md`：

```markdown
# <迭代ID> <主题>开发计划

> 计划状态：待执行 / 执行中 / 等待用户 / 阻塞 / 已完成 / 已取消
> 基线标识：<Git SHA / SVN revision / 文件快照标识>
> 初始工作区：<clean / dirty>
> 初始修改文件：<文件列表或 —>

## 1. 编码任务

| 任务ID | 目标 | 需求项 | 设计来源 | 依赖 | 状态 | 当前结果 |
|---|---|---|---|---|---|---|
| TASK-001 | <可交付行为> | REQ-001 | <设计章节或最小约束> | — | 待执行 | — |

## 2. 验证清单

| 验证ID | 目标 | 需求项 | 执行方 | 状态 | 当前证据 |
|---|---|---|---|---|---|
| VERIFY-001 | <构建或场景> | REQ-001 | AI / 用户 | 待验证 | — |

状态：待验证 / 已通过 / 未通过 / 无法执行 / 待用户验收。

## 3. 当前阻塞

| ID | 阻塞内容 | 影响任务 | 需要谁处理 |
|---|---|---|---|
```

`当前结果` 只保存恢复所需的最新事实，例如主要修改文件、短变更摘要、局部检查或阻塞原因；`当前证据` 只保存命令/步骤、结果和证据位置。无内容章节省略。不添加时间线、Agent 名称/ID、状态变化历史、接口细节、完整路径清单、允许/禁止表或重复验收标准。并行与冲突仅在实际存在时增加一句说明。

计划整体、编码任务和验证项是不同状态层级：计划整体可使用“等待用户、已取消”，`TASK-xxx` 固定使用“待执行 / 执行中 / 已完成 / 阻塞 / 跳过”，`VERIFY-xxx` 使用上方验证状态。不同层级枚举不要求相同，也不得互相写入。

## 更新规则

只维护当前状态和当前结果。任务开始时写“执行中”；完成、阻塞或跳过时立即回写状态、短结果和必要证据。验证后回写状态与当前证据；版本控制存在时由其保存历史，没有时由基线和当前结果支持恢复。主要内容改变时同步 `progress.json` 的当前任务和里程碑。

## 完成前自检

在标记计划可执行或写入“建议查阅”前执行。未通过项先修正；前置文档未确认或活动阻塞未清零时，只记录阻塞。

- 计划是否只回答任务、状态、依赖、验证和阻塞？
- 是否没有复制需求事实、详细技术设计或 UI 原型内容？
- `TASK-xxx` 是否都是编码或必要技术产物，`VERIFY-xxx` 是否都是执行性验证？
- 是否避免按文件、函数、类或工具数量过细拆分？
- 是否记录基线、初始工作区和初始修改文件？
- 任务和验证项是否具有恢复所需的当前结果或证据字段？
- 是否区分计划整体、`TASK-xxx` 和 `VERIFY-xxx` 三类状态，没有混用枚举？
- 是否没有时间线、Agent 名称/ID 和状态变化历史？
