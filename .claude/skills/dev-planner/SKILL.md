# Dev Planner - 开发计划

## 定位

`dev-planner` 不重新决定“要做什么”。需求范围来自 `spec-analyzer`，影响范围来自 `impact-analyzer`，实现候选任务来自 `design-writer` 和 `ui-designer`。

它只负责把这些输入整理成可执行、可恢复、可审查的开发计划：

- 任务按什么顺序执行。
- 哪些任务可以并行。
- 哪些任务有依赖或文件冲突。
- 哪些任务来自详细设计，哪些来自跳过详细设计的实现要点。
- 后续 `dev-builder` 应该如何逐任务推进并记录状态。

---

## 核心原则

1. **计划服务于执行。** 每个任务必须细到 `dev-builder` 能直接派发给实现者执行；不能出现“实现全部功能”这类粗任务。
2. **不重新设计。** 不新增需求、不改设计决策、不重新做 UI 设计。发现输入缺口时记录阻塞项。
3. **被依赖的先做。** 数据结构和接口提供方先于调用方；基础配置先于业务逻辑；业务状态先于 UI 绑定。
4. **高风险先验证。** 接口不确定、数据迁移、跨模块调用、UI 技术不确定性等任务前置。
5. **冲突要显式。** 修改同一文件、同一接口、同一配置或同一 UI 组件的任务必须标注冲突。
6. **状态可恢复。** 开发计划初始化任务状态；执行状态由 `dev-builder` 后续更新。

## 输入

| 输入 | 用途 |
|------|------|
| 需求设计文档：`docs/design/需求/<需求迭代编号>-<需求主题>需求.md` | 提取进入详细设计的需求项、实现任务、编码上下文、验证计划 |
| 界面设计文档：`docs/design/ui/<需求迭代编号>-<需求主题>界面设计.md` | 提取 UI 实现任务、界面契约、前端目标文件、UI 验收方式 |
| `impact-analyzer` 输出 | 提取跳过详细设计的需求项、微需求项实现要点、影响面、聚合风险 |
| 代码探查结果 | 辅助确认任务依赖、文件冲突、测试入口 |

没有 UI 影响时，不需要界面设计文档。

---

## 输出

写入：

```text
docs/design/计划/<需求迭代编号>-<需求主题>开发计划.md
```

开发计划是执行状态的载体，不写回需求设计文档。

---

## 工作流程

### Step 1：读取输入

确认本次迭代有哪些任务来源：

| 来源 | 处理方式 |
|------|---------|
| 进入详细设计的需求项 | 从需求设计文档的“实现任务 / 编码上下文 / 验证计划”提取任务 |
| 涉及 UI 的需求项 | 从界面设计文档的“前端实现设计 / 编码边界 / 验收方式”补充任务 |
| 跳过详细设计的需求项 | 从 `impact-analyzer` 的实现要点生成轻量任务 |
| 微需求项 | 生成单步任务，必须带验收标准 |

如果某个需求项既有需求设计文档又有界面设计文档，任务必须关联同一个需求项 ID。

### Step 2：规范化任务

把所有来源统一成任务项：

| 字段 | 说明 |
|------|------|
| 任务ID | `TASK-001` 格式，按最终执行顺序编号 |
| 任务名 | 动词开头，描述具体动作 |
| 来源需求项 | 关联 `REQ-xxx` |
| 来源文档 | 需求设计文档 / 界面设计文档 / impact-analyzer |
| 类型 | 前置验证 / 基础改动 / 功能实现 / UI 实现 / 联调验证 / 收尾 |
| 目标文件 | 预计修改或新增的文件、接口、配置、组件 |
| 输入 | 设计决策、界面契约、实现要点、接口或数据契约 |
| 输出 | 代码、配置、测试、文档回写 |
| 验收标准 | 可执行、可检查 |
| 状态 | 初始为“待执行” |

任务粒度要求：

- 单任务应尽量控制在一个明确目标内。
- 可以跨少量文件，但不能跨多个互不相关模块。
- UI 任务必须引用界面契约或现有界面模式。
- 低置信度事项不得进入任务项，进入阻塞项。

### Step 3：分析依赖与冲突

对每个任务检查：

```text
□ 是否依赖数据结构、配置项或迁移？
□ 是否依赖接口提供方？
□ 是否依赖业务状态或后端返回字段？
□ 是否依赖 UI 组件、路由、窗口或页面载体？
□ 是否修改同一文件或同一组件？
□ 是否存在同一接口的调用方/提供方顺序问题？
□ 是否需要测试数据、模拟数据或现场配置？
```

输出依赖、冲突和可并行关系。不能确认时记录阻塞项。

### Step 4：生成阶段序列

按实际任务生成阶段，不要求每个阶段都存在：

| 阶段 | 适用任务 |
|------|---------|
| 阶段 1：前置验证 | 高风险探针、接口/数据/UI 技术可行性确认 |
| 阶段 2：基础改动 | 数据结构、配置项、接口契约、模型、公共组件 |
| 阶段 3：功能实现 | 业务逻辑、服务、状态流、接口调用 |
| 阶段 4：UI 实现 | 页面、窗口、组件、字段、交互、状态展示 |
| 阶段 5：联调验证 | 跨模块串联、端到端流程、回归测试 |
| 阶段 6：收尾 | 文档回写、兼容/升级、提交准备 |

排序规则：

1. 被依赖任务在前。
2. 高风险任务尽早。
3. 同文件冲突任务串行。
4. 无依赖且无冲突任务标注可并行。
5. UI 任务依赖的数据字段、接口和业务状态必须先完成，除非可以用 mock 明确解耦。

### Step 5：初始化状态

任务状态枚举：

| 状态 | 含义 |
|------|------|
| 待执行 | 已纳入计划，尚未开始 |
| 执行中 | `dev-builder` 正在处理 |
| 已完成 | 编码和对应验证通过 |
| 阻塞 | 缺少输入、依赖失败或需要人工确认 |
| 跳过 | 本轮明确不执行，并说明原因 |

`dev-planner` 只初始化状态为“待执行”或“阻塞”。后续状态由 `dev-builder` 更新。

## 自审查

输出前检查：

```text
□ 是否仍在重新设计需求或 UI？
□ 是否包含所有进入详细设计的需求项任务？
□ 是否包含跳过详细设计的需求项和微需求项？
□ 涉及 UI 的任务是否引用界面设计文档或界面契约？
□ 每个任务是否有来源需求项、目标文件、验收标准？
□ 依赖、冲突、并行关系是否明确？
□ 低置信度事项是否进入阻塞项？
□ 任务状态是否初始化，且支持 dev-builder 后续更新？
```
