# Impact Analyzer — 影响面分析

## 定位

验证 `spec-analyzer` 输出的需求项初判级别，量化实际代码影响范围，并判定后续流程深度。

本 Skill 只回答：

```text
这个需求项实际影响哪些文件、模块、接口、数据和 UI？
初判级别是否需要升级？
是否需要进入详细设计？
是否需要 ui-designer？
如果跳过详细设计，dev-builder 需要哪些实现要点？
```

本 Skill 不负责：

- 重新拆需求项。需求项拆解由 `spec-analyzer` 完成。
- 编写详细设计。详细设计由 `design-writer` 完成。
- 生成界面契约。界面契约由 `ui-designer` 完成。
- 编码、测试或提交。

---

## 铁律

1. **无证据不输出结论。** 每项影响结论必须绑定证据来源：工具名、查询语句或扫描路径、返回摘要。
2. **必须量化。** 受影响文件数、模块数、接口数、数据对象数必须是具体数字，禁止写“若干”“可能”“相关模块”。
3. **级别只能升不能降。** 实际范围小于初判时保留初判级别；实际范围更大时升级。
4. **聚合风险不粗暴改级别。** 聚合风险单独记录，用于提高开发计划、测试和审查深度，不直接把所有需求项统一升级。
5. **待确认项不得伪装成事实。** 工具无法证明的结论写入“待人工确认”。

---

## 触发条件

- `spec-analyzer` 产出需求文档后。
- 用户要求“分析影响面”“看看会改哪些地方”。
- 需求文档中的需求项初判级别已确定。
- 回退流程要求重新分析影响面。

---

## 输入

- `spec-analyzer` 输出的需求文档：
  - 需求项ID
  - 中文级别 / 内部级别
  - 验收标准
  - 按层展开
  - UI 影响标记
  - 需求项依赖关系
  - 聚合风险
- 项目代码仓库路径。
- 可用代码索引或静态扫描工具。

---

## 数据源与降级链

按优先级依次尝试。不可用的工具自动跳过。

| 优先级 | 工具 | 适用场景 |
|--------|------|----------|
| 1 | GitNexus | AST 级：模块依赖、接口签名、数据模型、调用链 |
| 2 | codegraph | 文件级：模块成员、调用关系 |
| 3 | 其他知识图谱工具 | 按工具能力自行适配 |
| 最终 | grep / glob 静态扫描 | 头文件声明、接口引用、SQL 表名、枚举定义、UI 组件引用 |

### 降级策略

```text
当前工具可用 → 使用
  ↓ 不可用（CLI 无响应 / 索引未构建 / 权限不足）
下一优先级 → 使用
  ↓
全部不可用 → 保守模式
```

保守模式规则：

- 默认将当前需求项级别升级一级：微→小，小→中，中→大。
- 如果静态扫描仍能证明微需求项满足“<=2 文件 + 不改接口 + 不改 DB + 不改行为逻辑 + 零歧义”，可保留微。
- 输出中必须明示：`知识图谱不可用，已按保守策略处理`。

## 工作流程

### Step 1: 提取查询目标

对每个需求项列出需要验证的信息项。

| 验证项 | 查询内容 | 证据要求 |
|--------|----------|----------|
| 受影响文件 | 需求项预期文件是否完整？是否遗漏调用方、配置、测试、升级脚本？ | 文件路径列表 + 工具名 |
| 模块归属 | 每个文件属于哪个模块？跨几个模块？ | 模块名 + 归属来源 |
| 接口变更 | 是否涉及对外接口、头文件、proto、RPC、HTTP、事件消息？ | 接口签名或文件路径 |
| 数据变更 | 是否涉及表结构、配置结构、持久化字段、枚举、缓存结构？ | 表名/字段/结构体/文件路径 |
| 协议变更 | 是否涉及跨服务通信协议或兼容策略？ | proto 文件、消息定义、版本策略 |
| UI 影响 | 是否涉及页面、组件、表单、文案、状态或交互路径？ | UI 文件、组件名、路由、截图/稿件来源 |
| 测试影响 | 是否存在现有测试、demo、回归入口？ | 测试文件、脚本、命令或缺失说明 |

### Step 2: 执行证据查询

逐需求项、逐验证项查询，记录证据。

输出记录格式：

```markdown
### REQ-001 查询记录

| 验证项 | 工具 | 查询语句/路径 | 结果 | 证据状态 |
|--------|------|---------------|------|----------|
| 受影响文件 | GitNexus | ... | 5 个文件：... | 已确认 |
| 接口变更 | grep | ... | 1 个接口：... | 已确认 |
| UI 影响 | glob | ... | 2 个页面组件：... | 已确认 |
| 数据变更 | grep | ... | 未发现 | 已确认 |
```

证据状态只能使用：

- `已确认`
- `待人工确认`
- `无证据`

### Step 3: 确认单个需求项级别

将代码证据与 `spec-analyzer` 初判逐项对比。

| 证据结果 | 动作 |
|----------|------|
| 受影响文件、模块、接口、数据范围大于初判 | 升级当前需求项 |
| 发现初判未包含的接口变更 | 升级当前需求项 |
| 发现初判未包含的数据变更 | 升级当前需求项 |
| 发现协议、跨仓库、不可回滚 DB、Breaking Changes | 升级为大 |
| 实际范围小于初判 | 不降级，保留初判 |
| 证据不足 | 标记待人工确认；必要时按保守模式升级 |

单个需求项级别由该需求项自身影响决定，不因其他需求项复杂而直接升级。

### Step 4: 分析聚合风险

合并本迭代所有需求项的实际影响数据，记录聚合风险。

聚合风险不直接粗暴升级所有需求项。它影响：

- `dev-planner` 的任务排序和冲突标记。
- `code-tester` 的测试深度。
- `code-review` 的回归风险审查范围。
- 是否需要提醒用户将大范围需求拆分为多轮迭代。

聚合风险输出格式：

```markdown
## 聚合风险

| 风险 | 涉及需求项 | 证据 | 影响 | 后续处理 |
|------|------------|------|------|----------|
| 文件重叠 | REQ-001, REQ-003 | both modify PartConfig.cpp | 需要串行开发 | dev-planner 排序，code-tester 加回归 |
```

可记录风险：

- 文件重叠。
- 模块重叠。
- 接口共享。
- 数据结构共享。
- UI 字段和服务端字段命名/默认值耦合。
- 多个小需求项组合后形成跨模块风险。

### Step 5: 判定是否进入详细设计

对每个需求项回答以下问题：

```text
1. 是否新增或修改接口、数据结构、协议、配置结构？
2. 是否存在多个交互或业务流程分支需要决策？
3. 是否涉及新的错误处理路径、状态变迁、兼容策略？
4. 是否涉及跨模块数据一致性、缓存一致性或升级兼容？
5. 是否存在低置信度项，需要通过详细设计澄清？
```

判定规则：

| 判断结果 | 动作 |
|----------|------|
| 全部为否 | 跳过详细设计 |
| 任意一项为是 | 进入详细设计 |
| 有待人工确认且影响编码边界 | 进入详细设计或回需求分析确认 |

跳过详细设计的需求项，必须输出“实现要点”。实现要点要具体到 dev-builder 可直接组装编码输入，不能写“按现有逻辑处理”。

### Step 6: 判定是否需要 ui-designer

对每个需求项确认 UI 影响是否成立。

| 情况 | 动作 |
|------|------|
| spec-analyzer 标记 UI影响=否，代码证据也无 UI 文件 | 不触发 ui-designer |
| spec-analyzer 标记 UI影响=是，且存在 UI 文件/组件/页面证据 | 触发 ui-designer |
| spec-analyzer 标记 UI影响=是，但找不到 UI 证据 | 标记待人工确认；必要时触发 ui-designer 先澄清 |
| spec-analyzer 未标记 UI，但扫描发现 UI 文件受影响 | 升级 UI 影响，触发 ui-designer |

ui-designer 输入应包含：

- 需求项ID。
- UI 影响描述。
- 相关页面/组件文件。
- 用户提供的 UI 稿、截图或原型路径（如有）。
- 现有同类界面模式证据。

### Step 7: 输出需求影响分析文档

写入 `docs/02-需求/<迭代前缀>-<需求主题>影响面.md`。

与需求文档同名、同目录，便于下游读取。

---

## 输出格式

```markdown
# 需求影响分析 — vX.X：<需求主题>

## 分析信息
- 分析日期：YYYY-MM-DD
- 分析工具：GitNexus / codegraph / grep / glob
- 数据源：

## 级别确认

| 需求项ID | 需求项 | 初判级别 | 确认级别 | 文件数 | 模块数 | 接口变更 | 数据变更 | UI影响 | 详细设计 | ui-designer | 证据 |
|----------|--------|----------|----------|--------|--------|----------|----------|--------|----------|-------------|------|
| REQ-001 | xxx | 小/S | 中/M | 5 | 2 | 是 | 否 | 是 | 进入 | 需要 | EVID-001 |

## 影响明细

### REQ-001：<需求项名称>

| 类型 | 路径/对象 | 影响 | 操作 | 证据 | 置信度 |
|------|-----------|------|------|------|--------|
| 文件 | src/... | 修改字段映射 | 改 | EVID-001 | 高 |
| 接口 | XxxService::save | 新增参数 | 改 | EVID-002 | 高 |
| UI | PartConfigPanel | 新增输入项 | 改 | EVID-003 | 中 |

## 级别调整记录

| 需求项ID | 初判 | 确认 | 调整原因 |
|----------|------|------|----------|
| REQ-001 | 小/S | 中/M | 发现接口变更和 2 个模块影响 |

## 跳过详细设计的需求项

| 需求项ID | 跳过理由 | 实现要点 |
|----------|----------|----------|
| REQ-002 | 5 问全否 | 修改 xxx 文件中的错误码映射，不改接口、不改数据结构 |

## 需要详细设计的需求项

| 需求项ID | 原因 | design-writer 输入 |
|----------|------|--------------------|
| REQ-001 | 接口变更 + UI 变更 | 需求项 + 影响明细 + 证据 |

## 需要 ui-designer 的需求项

| 需求项ID | UI 区域 | 证据 | 待确认 |
|----------|---------|------|--------|
| REQ-001 | 零件配置界面 | EVID-003 | 拍摄距离字段位置 |

## 聚合风险

| 风险 | 涉及需求项 | 证据 | 影响 | 后续处理 |
|------|------------|------|------|----------|
| 文件重叠 | REQ-001, REQ-003 | EVID-004 | 需串行开发 | dev-planner 排序 |

## 待人工确认

| ID | 需求项 | 问题 | 影响 | 建议 |
|----|--------|------|------|------|
| TBD-001 | REQ-001 | 字段单位未确认 | 影响 UI 和校验 | 回用户确认 |
```

---

## 与下游的衔接

| 判定结果 | 下游 |
|----------|------|
| 进入详细设计 | 调用 `design-writer`，传入需求项 + 影响明细 + 证据 |
| 跳过详细设计 | 调用 `dev-builder`，传入需求项 + 实现要点 + 影响明细 |
| UI 影响成立 | 调用 `ui-designer`，传入 UI 文件/组件证据和用户稿件 |
| 聚合风险高 | 通知 `dev-planner` 提高排序和冲突处理深度；通知 `code-tester` 提高测试深度 |
| 待人工确认阻塞编码 | 回到用户确认，或回 `spec-analyzer` 修正需求文档 |

---

## 文档 CRUD

| 操作 | 行为 |
|------|------|
| 新建 | `spec-analyzer` 完成后，生成 `<前缀>-<主题>影响面.md` |
| 读取 | `design-writer` / `ui-designer` / `dev-builder` / `dev-planner` 读取当前迭代文件 |
| 更新 | 回退触发重新分析时覆盖原文件，并在文档中记录调整原因 |
| 删除 | 不删除。历史迭代文件保留备查 |
```
