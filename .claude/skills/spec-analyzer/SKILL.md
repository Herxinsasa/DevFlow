# Spec Analyzer - 需求规格

## 职责

回答“要做什么”。只整理用户目标、范围、行为规则和验收事实，不设计实现，不把 AI 推测写成需求。

## 工作原则

- 不确定项只有在不同答案会改变行为、范围、UI、数据、错误处理、兼容或验收时才阻塞；影响编码时必须确认，不得自行选择默认答案。
- 每个需求项必须能独立理解和验收，业务背景只保留会改变当前决策的内容。
- 需求描述写业务事实和可观察结果，不写目标文件、类、接口实现或任务拆分。
- 用户确认后把结论写回正文并删除已解决问题，避免旧问题继续污染下游。

每个 `REQ-xxx` 至少明确：

```text
名称 / 目标 / 触发条件 / 正常路径 / 验收标准 / UI影响 / 当前阻塞
```

异常场景、依赖、兼容要求、数据口径和非目标在实际影响行为或验收时必须补充；没有内容时省略，不填充空模板。

## 触发边界

- 新增或改变产品行为时触发。
- T0 有明确输入、输出或使用规则时生成极简规格。
- 纯文档、格式、注释和不改变行为的局部维护可跳过。
- Bug 修复不触发；若预期行为需要改变，先经用户确认转为需求。

## 输入

- 用户的需求描述、需求文档、Issue、截图说明或口头需求。
- 用户提供的 UI 稿、截图、Figma、Pencil、HTML 原型。
- 已有需求文档、历史迭代文档或项目事实。

## 输出

使用模板：

```text
references/需求规格_模板.md
```

写入路径：

```text
docs/02-需求/<迭代ID>-需求.md
```

需求规格生成后必须提示用户确认；未确认不得自动进入 `impact-analyzer`。

## 工作步骤

1. 将输入拆成可独立验收的 `REQ-xxx`，耦合行为可放在同一迭代。
2. 只追问不同答案会改变行为、范围、UI、数据、错误处理、兼容性或验收结果的问题。
3. 可从可靠项目事实推导的内容须标明依据；无法可靠推导且影响编码的内容列为阻塞问题。
4. 涉及算法输出时按需确认：适用范围、显示条件、无值/旧数据行为、单位精度、自动流程与查询范围、持久化历史。
5. 涉及 UI 时写清业务规则，不做布局、视觉或技术实现设计。
6. 新对象、模式、状态、枚举值或规则与既有对象存在继承、扩展、替代或差异关系时，按需记录参考对象、一致行为和差异行为；无法确认且影响验收时列为阻塞问题。
7. 记录需求项依赖和聚合风险。多个需求项共同交付导致回归、联调或测试加深时，只写短结论，不提升单项等级。
8. 用户答复后把结论写回当前事实并删除已解决问题。
9. 为每个需求项记录 T0-T3 初判级别。使用模板：`references/需求规格_模板.md`，输出 `docs/02-需求/<迭代ID>-需求.md`。T0/T1 同文附简要影响结论；T2/T3 后续独立分析。

## 分级初判

按业务传播、契约风险和失败后果初判 T0-T3。多个文件、函数或相同工具接入不自动升级；独立新类不自动升级。最终等级由影响面核实。

## 门禁

文档状态为“已确认”且活动阻塞为零后才继续。完成时提示用户查阅并明确“需要确认”。确认摘要只列需求数量、等级、UI 影响和未决问题，不复述分析过程。

## 完成前自检

在提示用户确认需求规格前执行。未通过项先修正；影响编码的歧义未清零时，不得进入影响面、计划或编码。

- 每条需求是否可验收且没有实现细节？
- 每个需求项是否包含目标、触发条件、正常路径、验收标准、UI 影响和当前阻塞？
- 实际涉及的异常场景、依赖、兼容、数据口径和非目标是否明确？
- UI 显示/隐藏、格式和异常规则是否在实际涉及时明确？
- 新对象或语义关系是否在需要时明确了一致行为和差异行为？
- 需求依赖和聚合风险是否已记录或确认不涉及？
- 阻塞级待确认问题是否归零后才允许流转？
- 表格是否遵守模板填写规则？
- 是否删除已解决问题和无内容章节？
