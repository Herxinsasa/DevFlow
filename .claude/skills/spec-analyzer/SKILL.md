# Spec Analyzer - 需求规格

## 定位

回答“要做什么”。只整理用户目标、范围、行为规则和验收事实，不设计实现，不分析代码影响，不把 AI 推测写成需求。

## 触发边界

- 新增或改变产品行为、接口、数据、UI 或配置规则时触发。
- T0 只要存在可观察行为，也生成极简规格。
- 纯文档、格式、注释和不改变行为的局部维护可跳过。
- Bug 修复不触发；若正确预期需要改变，经用户确认后转为需求开发。

## 工作原则

1. **事实可确认。** 需求只写用户输入、可靠项目事实和用户已确认结论；AI 推断不得写成目标事实。
2. **结果可验收。** 每个 `REQ-xxx` 能独立说明目标、触发条件、正常行为和可观察验收结果。
3. **只问关键问题。** 不同答案会改变行为、范围、UI、数据、错误、兼容或验收时才作为阻塞问题。
4. **职责不越界。** 不写目标文件、类、接口实现、影响链路、技术方案或任务拆分。
5. **确认后流转。** 需求规格生成或实质修订后必须暂停；用户明确确认前不得进入影响分析。

异常场景、依赖、兼容要求、数据口径、非目标和语义关系只在实际影响行为或验收时记录，无内容时省略。

## 文档准备

仅在生成或实质修改需求规格前读取适用项目文档规范；项目未覆盖的部分读取 `.claude/constraints/document-req.md`。恢复阶段已读取的约束可复用；新会话、新执行 Agent 或约束变化后重新读取。

## 输入

- 用户的需求描述、需求文档、Issue、截图说明或口头需求。
- 用户提供的 UI 稿、截图、原型或交互说明。
- 与业务预期有关的已有需求文档、历史确认和项目事实。

只读取澄清业务目标所需的信息，不为编写需求规格扫描实现细节。

## 工作流程

### Step 1：确定本次边界

识别本次目标、业务场景、包含范围和明确非目标。业务场景只说明谁在什么情况下需要本次变化，不扩写项目背景或方案理由。独立新输入创建新迭代；同一迭代的补充更新原需求规格。

### Step 2：形成需求项

按可独立理解和验收的行为组织 `REQ-xxx`。耦合行为可以保留在同一迭代，但必须说明依赖；不按文件、函数或预计任务数量拆分。

每个需求项按 `references/需求规格_模板.md` 记录目标、触发与前置条件、正常行为与结果、验收标准、UI 影响和当前阻塞。实际涉及异常、数据口径、兼容或语义关系时补充对应事实。

需求项以表格为默认表达。只有业务规则、外部边界、异常或兼容事实无法在一行内清楚表达，并且会改变行为、验收或影响分析范围时，才在对应需求项下展开；简单需求不展开。补充内容只记录已确认的业务事实和可观察结果，不写代码位置、组件协作、字段结构、接口实现或任务拆分。

### Step 3：收敛待确认问题

优先从用户当前说明和可靠项目事实中补齐信息。无法证明且不同答案会影响行为、范围、契约或验收时，集中列为当前阻塞问题，不自行选择默认答案。

用户答复后把结论写回对应需求项，删除已解决问题；与本次实现无关的问题移入非目标，不把旧 TBD 带入下游。

### Step 4：初判等级与后续需求

按业务传播、契约风险和失败后果初判 T0-T3，并记录 UI 影响。文件、函数、调用点或重复接入数量不直接决定等级，最终等级由影响分析核实。

### Step 5：写入需求规格

使用 `references/需求规格_模板.md` 写入：

```text
docs/02-需求/<迭代ID>-需求.md
```

首次生成或实质修订后将文档状态设为“待确认”。T0/T1 的简要影响结论由后续 `impact-analyzer` 写回同一文档；T2/T3 使用独立影响面文档。

### Step 6：等待用户确认

向用户提供文档路径和简短确认摘要，只列需求数量、初判等级、UI 影响和当前阻塞，并明确标记“需要确认”。同步将当前流程置为 `waiting_confirmation`，然后停止，不自动调用 `impact-analyzer`。

用户明确确认后，将文档状态更新为“已确认”；只有活动阻塞为零时才能进入影响分析。用户提出修改时更新原文档并再次保持“待确认”。

## 完成前自检

在提示用户确认前执行：

- 文档是否用短结论说明了本次业务场景，没有扩写无关背景？
- 每个需求项是否能独立理解和验收？
- 目标、触发与前置条件、正常行为与结果、验收标准、UI 影响和当前阻塞是否齐全？
- 实际涉及的异常、依赖、兼容、数据口径、非目标或语义关系是否明确？
- 复杂需求的外部边界是否足以供影响分析定位检索方向，同时没有混入技术设计？
- 是否没有写实现位置、技术方案、影响链路或任务拆分？
- AI 推断是否没有被写成需求事实？
- 已解决问题和空章节是否已删除？
- 文档是否处于“待确认”，且流程已暂停而不是自动进入下一阶段？
