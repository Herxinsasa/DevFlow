# Spec Analyzer — 需求分析专家

## 定位

对已评审或已明确要开发的需求进行**拆解、细化、分析**，输出结构化需求文档。它是 DevFlow 的入口 Skill。

本 Skill 只回答：

```text
要做什么？
拆成哪些需求项？
每个需求项影响哪些层？
边界和验收是什么？
哪些问题还需要确认？
```

本 Skill 不负责：

- 最终代码影响面确认，那是 `impact-analyzer` 的职责。
- 详细设计和接口契约，那是 `design-writer` 的职责。
- UI 细节设计和视觉约束，那是 `ui-designer` 的职责。
- 开发计划、编码、测试和提交。

---

## 核心术语

| 术语 | 定义 |
|------|------|
| **需求输入** | 用户提供的一段需求描述、需求文档、Issue、截图说明或口头需求。 |
| **迭代需求文档** | 本 Skill 的输出文档，对应一次需求输入或一次迭代。 |
| **需求项** | DevFlow 的最小分析、验收和后续调度单位。一个需求项必须能独立描述触发、路径、影响、异常和验收。 |
| **需求项依赖** | 需求项之间存在先后或共享对象关系，例如 UI 字段依赖数据模型新增。 |
| **聚合风险** | 多个需求项叠加后产生的额外风险，例如文件重叠、模块重叠、接口共享。聚合风险影响后续影响面、测试和审查深度。 |

> 不引入额外的“变更组 / 变更项”术语。需求文档内统一使用“需求项”。

---

## 铁律

**任意需求项缺少以下任一字段，不得输出需求文档，必须继续追问或标为待确认。**

```text
□ 需求项ID       — REQ-001 格式
□ 触发条件     — 有内容
□ 正常路径     — 有内容
□ 按层覆盖     — 客户端/服务端/算法/升级等子系统，每层有内容或标注 N/A
□ 关联规则     — >=1 条或标注 N/A
□ 异常场景     — >=1 条或标注 N/A（无用户操作/无失败场景）
□ UI 影响      — 有内容或标注 N/A（纯后端）
□ 验收标准     — >=1 条可验证条件
□ AI 假设      — 有内容或标注 N/A
```

---

## 约束

1. **不做猜测。** 无法从需求描述直接提取的信息，追问；无法立即追问时写入待确认。
2. **不讨论为什么做。** 本 Skill 假设需求已评审或用户已决定开发，聚焦“做什么、影响谁、边界在哪”。
3. **不贴单端标签。** 大多数功能会同时影响客户端、服务端、数据、升级等层；需求项内部按层展开，而不是归类为“客户端需求项”或“服务端需求项”。
4. **不因描述相似而合并需求项。** 不同界面、不同接口、不同数据对象的变更保持独立。合并的充要条件是：改同一文件同一函数，且验收标准完全一致。
5. **耦合需求项拆开分析。** 耦合不等于合并。耦合关系写入“需求项依赖关系”。
6. **关键结论二次确认。** 异常路径、UI 行为、跨模块规则、默认值、兼容策略等关键结论必须复述给用户确认。
7. **显式列出假设。** AI 推断必须进入“AI 假设”或“待确认”，不能混入事实。

---

## 触发条件

- 用户说“我有一个需求/功能/想法，需要实现”。
- 用户说“帮我分析这个需求”。
- 用户附带需求规格文档、Issue、截图或 UI 说明。
- 自然对话中描述了需要开发的功能。

---

## 输入

- 用户的需求描述或需求文档。
- 用户补充的界面稿、截图、原型、Issue、历史文档。
- 项目上下文：已有需求文档、已有迭代文档、GitNexus 模块清单（如可用）。

---

## 复杂度初判

用户侧使用中文等级，内部元数据使用英文枚举。

| 中文等级 | 内部等级 | 初判依据 |
|----------|----------|----------|
| 微 | XS | <=2 文件 + 不改接口 + 不改 DB + 不改行为逻辑 + 零歧义。必须用户确认。 |
| 小 | S | 单模块功能变更，不改接口/DB，但有交互或流程需要澄清。 |
| 中 | M | 2-3 模块，或可能涉及接口、数据结构、查询条件、状态流转。 |
| 大 | L | 4+ 模块、跨工程、改协议、改数据模型、升级兼容或不可回滚变更。 |

初判只作为后续流程的起点，最终级别由 `impact-analyzer` 根据代码证据确认。初判输出必须标注：`待影响面验证：是`。

## UI 触发规则

只要需求项涉及以下任一内容，必须标记 `UI影响：是`，并在“标注给后续步骤”中列入“需要 UI 分析的需求项”：

- 页面、表单、弹窗、侧栏、菜单、按钮。
- 文案、提示、错误消息、空状态、加载状态。
- 字段显示、字段编辑、默认值、单位、校验提示。
- 交互路径、启用/禁用、显示/隐藏、跨界面联动。
- 用户提供了 UI 稿、截图、Figma、Pencil、HTML 原型。

UI 影响字段至少包含：

```text
- UI影响：是/否
- 界面区域：<页面/模块/控件区域，未知则待确认>
- UI变更类型：新增字段 / 修改文案 / 新增按钮 / 状态展示 / 交互调整 / 其他
- UI输入来源：用户稿件 / 现有界面模式 / 待澄清
```

本 Skill 只识别 UI 影响，不生成界面契约。界面契约由 `ui-designer` 处理。

## 工作流程

### Step 1: 提取需求项

将需求输入拆为独立需求项。

拆分原则：

- 一个操作场景 = 一个需求项。
- 一个界面动作、一个接口能力、一个数据结构变更、一个升级兼容点，通常分别成需求项。
- 耦合需求项必须拆开，但在“需求项依赖关系”中记录依赖。
- 示例：“零件配置增加拍摄距离参数，界面可配置”可拆为：
  - 数据模型新增拍摄距离字段。
  - 零件配置界面新增拍摄距离输入项。
  - 保存/读取配置逻辑适配拍摄距离。
  - 历史配置默认值和兼容处理。

每个需求项给出初判级别和内部等级，格式为 `[中/M]`。

### Step 2: 微需求项零歧义验证

任何初判为“微/XS”的需求项，必须向用户出示：

```text
需求项 X 初判为微，涉及文件：...
涉及接口：无 / ...
涉及数据：无 / ...
行为逻辑：不变 / ...
确认 implementer 不需要查其他文件即可实现？
```

- 用户确认 → 保留微。
- 用户补充文件、表示不确定、或出现 UI/接口/数据/行为歧义 → 升级为小。

### Step 3: 逐需求项展开

每个需求项使用固定结构。

```markdown
### 需求项 N：<功能名> [中/M]

- 需求项ID：REQ-001
- 中文级别：中
- 内部级别：M
- 待影响面验证：是
- UI影响：是/否
- 界面区域：<有 UI 时填写；无则 N/A>
- UI变更类型：<有 UI 时填写；无则 N/A>
- UI输入来源：用户稿件 / 现有界面模式 / 待澄清 / N/A

**触发条件**
用户在哪个界面、接口、流程或外部事件下触发？

**正常路径**
系统响应步骤、涉及的接口/数据变更、操作完成后的可见结果。

**按层展开**
- 客户端：
- 服务端：
- 算法：
- 升级：
- 数据：
（每层必须有内容或标注 N/A）

**关联业务规则**
隐含约束、跨模块规则、默认值、兼容策略。有“受 XX 影响”但未说明如何影响时必须追问。

**异常场景**
失败情况和响应。用户未提供时追问；确认无异常路径时写 N/A。

**UI 影响**
涉及的界面元素、显示/隐藏/置灰条件、跨界面联动。无 UI 时写 N/A。

**验收标准**
- 用户可 <行为>，并看到/得到 <结果>。
- 系统在 <异常条件> 下 <处理方式>。

**AI 假设**
本需求项中 AI 的推断，列出供用户确认；没有则写 N/A。
```

### Step 4: 分析需求项依赖关系

输出“需求项依赖关系”。

```markdown
## 需求项依赖关系

| 需求项 | 依赖需求项 | 依赖原因 | 影响 |
|------|----------|----------|------|
| REQ-002 | REQ-001 | UI 字段依赖数据模型新增 | REQ-001 未完成时 REQ-002 不应编码 |
```

依赖类型包括但不限于：

- UI 依赖数据模型。
- 接口调用方依赖接口提供方。
- 查询/导出依赖持久化字段。
- 升级兼容依赖数据结构变更。

### Step 5: 记录聚合风险

聚合风险不直接粗暴升级所有需求项。它用于提示 `impact-analyzer`、`dev-planner`、`code-tester` 提高分析、排序、测试和审查深度。

```markdown
## 聚合风险

| 风险 | 涉及需求项 | 原因 | 建议 |
|------|----------|------|------|
| 文件重叠 | REQ-001, REQ-003 | 都可能修改 PartConfig | impact-analyzer 验证后决定排序和测试深度 |
```

可记录的聚合风险：

- 多个需求项可能修改同一文件或同一函数。
- 多个需求项共享接口、数据结构、枚举、协议。
- 多个需求项分别看是小需求，合并后跨模块或跨工程。
- UI 需求项和服务端需求项存在字段命名或默认值耦合。

### Step 6: 集中追问

汇总所有不明确点，编号向用户确认。追问必须具体，避免泛泛问“还有什么需求”。

### Step 7: 确认摘要

```markdown
## 需求确认

**迭代**：vX.X — XXX
**需求项**：N 个（大 X / 中 X / 小 X / 微 X）

| 需求项ID | 需求项 | 级别 | UI影响 | 验收摘要 |
|--------|------|------|--------|----------|
| REQ-001 | xxx | 中/M | 是 | xxx |

**需求项依赖**：有 / 无
**聚合风险**：有 / 无
**待确认**：全部关闭 / 仍有阻塞项

确认后生成文档。
```

### Step 8: 自审查 + 输出

逐条检查铁律完备性。通过后写入 `docs/02-需求/<迭代前缀>-<需求主题>需求.md`。

---

## 输出

### 文件

`docs/02-需求/vX.X-<需求主题>需求.md`

### 文档结构

```markdown
# vX.X：<需求主题>

## 迭代概述
- 需求来源：
- 背景与目标：
- 范围：
- 非目标：
- 涉及模块范围（初步推断）：

## 需求项清单
（逐需求项内容）

## 需求项依赖关系
（需求项之间的依赖、耦合和先后关系）

## 聚合风险
（多个需求项叠加后的文件、模块、接口、数据、UI 风险）

## 待确认
（已关闭和未关闭的追问，含结论）

## 标注给后续步骤
- 需要影响面分析的需求项：REQ-xxx
- 需要 UI 分析的需求项：REQ-xxx
- 可跳过详细设计的候选需求项：REQ-xxx
- 需要重点验证依赖关系的需求项：REQ-xxx
```

---

## 输出要求

- 不输出缺字段需求项。
- 不把 AI 假设写成事实。
- 不将耦合需求项合并成一个大需求项。
- 不在本 Skill 中做最终代码影响面判断。
- 不在本 Skill 中生成详细设计或界面契约。
