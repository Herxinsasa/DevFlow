# UI Designer - UI 稿设计分析与前端设计

## 定位

`ui-designer` 负责把 UI 相关需求转成 AI 编码可执行的界面契约和前端实现设计。

它不替代产品需求分析，也不替代 `design-writer` 的整体详细设计。它解决 UI 到前端实现之间最容易丢失的信息：

- UI 稿表达了哪些页面、组件、字段和状态。
- 哪些内容是本次需求必须实现的。
- 哪些交互、校验、状态、响应式和视觉约束会影响编码。
- 前端应该改哪些区域，不能擅自扩展哪些区域。
- 当前前端类型是 Web、Qt Widgets、Qt QML 还是混合形态。

首版目标是轻量走通流程，不建立完整视觉设计体系。

---

## 输入

| 输入 | 来源 | 说明 |
|------|------|------|
| 需求项 | `spec-analyzer` | UI 相关需求项、业务规则、验收标准、异常场景 |
| 影响面 | `impact-analyzer` | 受影响页面、组件、路由、接口、数据结构 |
| UI 稿 | 用户提供 | Figma、Pencil、截图、图片、HTML 原型、设计说明、标注稿 |
| 前端代码事实 | 代码探查 | 页面结构、组件层级、样式系统、路由、状态管理、接口调用 |
| 现有设计模式 | 代码或设计系统 | 组件规范、表单模式、弹窗模式、列表模式、错误提示模式 |

---

## 输出

默认输出到当前需求设计文档可引用的位置：

```text
docs/design/ui/<需求迭代编号>-<需求主题>界面设计.md
```

输出内容：

1. **UI 输入摘要**：UI 稿来源、覆盖页面、设计版本、与需求项的对应关系。
2. **前端类型识别**：Web、Qt Widgets、Qt QML、混合或未知。
3. **界面契约**：页面、组件、字段、布局、交互、状态、校验、视觉约束、响应式、验收方式。
4. **前端实现设计**：按前端类型输出目标文件、组件拆分、状态管理、数据映射和样式策略。
5. **差异与缺口**：UI 稿与需求项不一致、UI 稿缺失状态、无法确认的视觉或交互。
6. **编码边界**：允许修改、禁止修改、不得自行发挥的设计点。

`design-writer` 读取本输出后，在需求设计文档中引用“界面契约”。

## 工作模式

### 模式 A：已有 UI 稿

这是默认模式。用户提供了 Figma、Pencil、截图、设计标注或 HTML 原型时，优先解析现成 UI 稿。

处理原则：

- 以 UI 稿为主，不重新发明界面。
- 需求项和 UI 稿不一致时标出差异，不擅自取舍。
- UI 稿只覆盖默认态时，补充缺失状态清单。
- UI 稿没有标注具体交互时，优先参考现有前端模式；仍不明确则进入未决问题。

### 模式 B：没有 UI 稿，但现有系统有同类界面

当需求较小或系统已有成熟设计模式时，按现有模式输出最小界面契约。

适用场景：

- 表单新增字段。
- 列表新增列。
- 配置页新增参数。
- 弹窗新增校验或提示。
- 页面已有同类组件和交互模式。

处理原则：

- 复用现有页面布局、组件、间距、状态提示和校验方式。
- 只补本次需求需要新增或修改的 UI 契约。
- 不做新的视觉风格设计。

### 模式 C：没有 UI 稿，且现有系统无明确模式

此时进行最小化视觉和 UE 澄清。参考产品经理流程，但只收集当前需求编码所需信息，不做完整产品视觉规范。

每轮只问 1-2 个关键问题。优先确认：

| 维度 | 必须明确的问题 |
|------|---------------|
| 页面位置 | 新页面、已有页面区域、弹窗、侧栏、步骤页还是配置项 |
| 布局结构 | 字段、按钮、列表、卡片、分组的排列方式 |
| 交互流程 | 用户从哪里进入，操作后发生什么 |
| 状态处理 | 默认、加载、空数据、错误、禁用、成功反馈 |
| 视觉约束 | 是否必须沿用现有组件；是否有明确禁用的样式变化 |

不在此模式中收集完整品牌、配色、字体和动效体系，除非本次需求本身就是视觉体系变更。

## 工作流程

### Step 0：识别前端类型

先判断当前 UI 需求落在哪类前端：

| 类型 | 判断线索 |
|------|---------|
| Web | React、Vue、Angular、HTML、CSS、路由、浏览器、管理后台、H5 |
| Qt Widgets | QWidget、QDialog、QMainWindow、QTableView、QSS、信号槽 |
| Qt QML | QML、Qt Quick、qml 文件、property、Signal、Component |
| 混合 | WebView、Qt 内嵌 Web、客户端壳 + Web 页面 |
| 未知 | 影响面不足，无法判断 |

识别结果写入输出文档。未知时先从影响面和代码事实补查，不直接假设。

### Step 1：确认 UI 输入类型

判断本次 UI 输入属于哪类：

| 类型 | 处理方式 |
|------|---------|
| Figma / Pencil | 读取页面、Frame、组件、变量、标注、截图 |
| 截图 / 图片 | 解析页面结构、字段、状态、视觉层级 |
| HTML 原型 | 解析 DOM、样式、交互入口 |
| 文字设计说明 | 提取页面、组件、字段、交互和状态 |
| 无 UI 稿 | 进入模式 B 或模式 C |

记录 UI 稿版本、来源和覆盖范围。没有版本信息时写“未提供”。

### Step 2：需求项对齐

把 UI 内容映射到需求项：

| 需求项 | UI 覆盖情况 | 页面/组件 | 缺口 |
|--------|-------------|----------|------|
| REQ-001 | 已覆盖 / 部分覆盖 / 未覆盖 | | |

如果 UI 稿包含需求外内容，标为“超出需求范围”，不得自动进入编码任务。

### Step 3：解析界面契约

按页面和组件输出契约：

| 契约项 | 必填内容 |
|--------|---------|
| 页面/窗口 | 页面、路由、窗口、Dialog、Widget 或 QML Page |
| 入口 | 导航入口、按钮入口、菜单入口、配置入口 |
| 组件 | 组件名称、用途、是否新增、是否复用 |
| 字段 | 字段名、类型、默认值、校验、展示格式 |
| 操作 | 按钮、菜单、快捷操作、触发条件 |
| 状态 | 默认、加载、空数据、错误、禁用、成功 |
| 交互 | 输入、选择、保存、取消、联动、跳转 |
| 适配 | 桌面、窄屏、滚动、溢出、最小尺寸 |
| 视觉约束 | 间距、对齐、颜色、字号、图标、组件风格 |
| 验收方式 | 如何确认 UI 与需求和稿件一致 |

### Step 4：按平台输出前端实现设计

基于 Step 0 的前端类型读取对应参考文件，并输出实现建议。

通用字段：

| 项 | 内容 |
|----|------|
| 目标文件 | 页面、组件、样式、路由、状态、接口文件 |
| 组件拆分 | 新增组件、复用组件、禁止新建组件 |
| 数据映射 | UI 字段到接口字段、配置字段或本地状态 |
| 状态管理 | 本地状态、全局状态、缓存、表单状态或 Qt 模型属性 |
| 样式策略 | 复用现有 class/token/component/QSS/QML 样式，不引入新视觉体系 |
| 兼容策略 | 旧数据、默认值、权限、灰度、回退 |
| 测试建议 | UI 单测、组件测试、E2E、Qt 手工验证或自动化 UI 测试 |

### Step 5：差异和未决问题

必须记录以下问题：

- UI 稿和需求项不一致。
- UI 稿缺少关键状态。
- UI 稿字段与接口或数据结构不匹配。
- UI 稿包含超出需求范围的内容。
- 现有组件无法支撑 UI 稿设计。
- 视觉稿无法确认尺寸、间距、颜色或交互。
- 前端类型未知或混合边界不清。

低置信度内容进入未决问题，不进入前端实现设计。

### Step 6：输出并交给后续流程

输出界面设计文档后：

- `design-writer` 引用界面契约，纳入需求设计文档。
- `dev-planner` 根据前端实现设计拆任务。
- `dev-builder` 编码时读取编码边界和验收方式。
- `code-review` 对照界面契约检查偏离、遗漏、过度开发。

## 自审查

输出前检查：

```text
□ 是否识别了前端类型？
□ 是否优先解析了现成 UI 稿，而不是重新设计？
□ 是否完成需求项和 UI 稿的对齐？
□ UI 稿中超出需求范围的内容是否已标出？
□ 页面、组件、字段、状态、交互、校验是否具体？
□ 是否按 Web 或 Qt 输出平台化实现设计？
□ 是否说明复用现有组件和样式的策略？
□ 低置信度内容是否进入未决问题？
□ 输出是否能被 design-writer 直接引用为界面契约？
```
