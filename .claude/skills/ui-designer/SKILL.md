# UI Designer - 界面设计

## 定位

回答“界面如何呈现和操作”。DevFlow 面向既有项目迭代：项目已有 UI 时，实际页面、公共样式和交互模式是设计基线；只设计本次变化，不从零重做或自行引入新的视觉风格。

本 Skill 产出供用户确认的界面结构稿或按需视觉稿，不决定组件拆分、状态管理和接口映射，不直接编写 Qt、Web 等生产 UI。技术实现由 `design-writer` 和编码阶段负责。

## 触发条件

仅满足任一条件时调用：

- 用户明确要求界面结构、原型、界面稿或可视化效果。
- 新增页面，布局和交互需要用户确认。
- 现有页面的布局、视觉层级、组件形态或交互路径发生变化。
- 复杂状态或信息层级仅靠文字无法确认。

简单字段、文案、显隐规则或明确复用既有页面模式时通常跳过；但后续实现仍须读取目标页面和项目样式，不得自行改变界面风格。

## 输入

按优先级读取：

1. 用户当前确认、截图和界面稿。
2. 已确认需求规格中的 UI 业务事实。
3. 已闭合影响面中的页面入口和约束。
4. 受影响页面、同类页面、公共组件、主题样式、交互代码和可用运行截图。

必须实际读取足以判断界面的现有证据。Qt 项目按需查看 `.ui`、QML、QSS、相关界面代码或运行截图；Web 项目按需查看页面、组件、主题样式或运行页面。先确认页面入口、必须展示的信息、信息优先级、区域约束、关键操作顺序及实际存在的窗口或屏幕限制。需求未说明且现有界面不能唯一确定时，集中询问用户并停止，不自行选择布局。

## 交付模式

- **界面结构稿**：布局、区域层级、组件位置或主要交互发生变化时使用，表达区域划分、相对位置、主要控件、入口、关键操作和本次差异，不模拟颜色、字体、间距等视觉细节。用户不需要视觉稿，或项目样式无法可靠复刻时默认使用此模式。
- **视觉稿**：仅在用户明确要求视觉效果，或本次需求确实改变视觉表现且现有风格能够可靠参考时使用。

结构稿可以使用线框图、标注截图、低保真 HTML 或其他能直观看清布局的形式；文字布局树只能作为补充。不得为了展示效果用 HTML 等跨技术栈原型替代项目真实视觉基线。

## 工作原则

1. **继承基线。** 改造页面以目标页面为准；新增页面继承相邻页面、公共组件和项目样式。
2. **只设计变化。** 需求决定业务行为，现有 UI 决定可继承的呈现方式；两者都不能决定的部分才是新设计决策。
3. **证据可追溯。** 不得只声称“已查看现有风格”；输出时简要给出主要页面、截图或文件依据。
4. **确认稿不是实现。** 结构稿和视觉稿只确认界面事实，不代表 Qt、Web 等生产实现或精确运行效果。
5. **确认后流转。** 影响实现的界面事实未确认前，不进入详细设计、开发计划或 UI 编码。

## 工作流程

1. 从需求和影响面确定本次需要确认的页面、布局约束、状态与交互。
2. 实际读取目标页面或最接近的同类 UI，区分继承项、本次变化和待确认项。
3. 布局方向缺少必要事实且不能从现有 UI 唯一确定时，先询问用户；事实充分时再选择结构稿或视觉稿。
4. 生成最轻量但可直观确认的产物，只覆盖本次相关页面、区域、交互和必要状态。
5. 提供产物入口、主要基线、本次差异和待确认项，将状态置为“待确认”并停止。用户确认后记录最终界面事实，再进入详细设计或计划。

确认稿按实际需求覆盖正常、加载、空、错误、禁用或成功状态；不为形式完整补造无关状态。

## 输出

原型文件放在：

```text
docs/05-UI/原型/<迭代ID>/
```

按需生成简短索引，只记录状态、需求规格、产物入口、交付模式、覆盖范围、主要界面基线、已确认界面事实和活动阻塞；不固定增加基线差异表，也不记录工具选择过程、设计系统说明、技术实现或过程流水。

## 完成前自检

- 是否确实需要用户直观确认，而非机械触发？
- 影响布局方向的需求事实是否充分；不足时是否先询问而非直接设计？
- 是否实际读取了目标页面或同类 UI 证据？
- 是否继承项目已有视觉与交互模式，并且只设计本次变化？
- 是否正确选择结构稿或视觉稿，没有用无法可靠还原的视觉稿替代结构确认？
- 是否没有把确认稿当作生产实现，或自行决定 Qt/Web 实现方式？
- 影响实现的界面事实是否已确认；未确认时是否停止流转？
