# 工作流文档成稿约束

**加载时机**：开始生成或实质修改需求规格、影响面、详细设计和开发计划前加载。先遵循项目文档规范；项目未规定的部分使用本约束。纯读取、代码实现和仅更新既有状态字段不重复加载。

**职责**：本约束保证核心分析、设计与计划文档可阅读、可执行、可追溯；对应 Skill 模板决定文档类型、章节和字段。本约束不改变确认门、任务状态或版本控制授权。

## 1. 结构

- 严格使用对应模板的章节、顺序和表格。只在模板明确允许的位置增加条件章节；不临时增加同级大纲。
- 每个保留章节先给出该章节的结论、目的或边界，再给明细、表格、流程和例外。章节只有标题和零散材料时，应合并、补全或删除。
- 表格用于稳定、可比较的重复信息；正文用于结论、因果、边界和决策。两者不重复转述。
- 模板要求检查状态时，明确写“无外部依赖”“无活动阻塞”“无通知”等结论；其他无内容章节省略。

## 2. 内容

- 将用户对话转译为当前文档需要的事实、结论和约束，不复制口语、讨论过程或解释性原文。会影响实现、消费、兼容或验收的精确条件必须保留。
- 每项结论都应能回答：范围是什么、依据是什么、对后续谁产生什么作用。来自其他产物的事实引用稳定路径、章节或 ID，不复制大段原文，也不改写为新的事实。
- 只写已确认事实、实际证据和明确结论。未知事项写为待确认，并给出影响范围、所需信息或解除条件；不得用“待补充”“TBD”“……”代替。
- 文档只承担本产物职责：需求不写实现方案，设计不写任务排期，计划不复制技术细节，审查和测试不重述需求背景。
- 成稿前先按职责过滤输入：需求保留业务行为、边界和验收；影响面保留当前链路、受影响边界和定位依据；详细设计保留技术契约与实现约束；开发计划只引用事实源并管理执行状态。
- 源码、图谱和版本库直读用于证明结论，不原样倾倒。路径、库、类、方法、字段、变量和调用链只写入需要这些信息的定位或设计位置；在目标、业务行为和需求影响中转译为读者可确认的短结论。

## 3. 表达

- 标题只命名主题，不附带括号说明。路径、层级、关联需求、数量、条件和补充解释写入正文、元信息或表格。
- 使用项目既有术语、状态、需求 ID、任务 ID 和命名；没有项目约定时使用模板定义。首次出现的关键缩写或业务术语应在上下文中说明。
- 面向读者组织信息：先让读者知道结论和边界，再提供定位所需的细节。一个段落只表达一个核心事实，避免长句、标签堆砌和无主语的碎片句。
- 不写 Agent、工具调用、思维过程、无关 diff、会话流水或为了凑完整度的泛化说明。

## 4. 成稿检查

- 移除模板占位符、无意义空表格、重复标题和仅复述输入的段落。
- 读者不查会话也能确定本文件的范围、关键结论、未决事项及下一阶段所需输入。
- 修改既有文档时局部更新；保留仍有效的用户确认和历史结论，并同步受影响的引用、状态和交叉对照。
